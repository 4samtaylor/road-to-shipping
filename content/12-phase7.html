The "implement this specific thing" prompt
I'm building a game in C. I need you to implement [function name] with this signature: [signature]. It should: [bullet list of exact behaviors]. Follow the patterns already in my code. Don't add any dependencies I haven't mentioned. Don't write any other functions — just this one.
The "explain before I use it" prompt
Before I use this code, explain to me: (1) what each function does in plain English, (2) what could go wrong if inputs are invalid, (3) anything I should change for my specific use case: [paste code]
The "I'm stuck on a bug" prompt
I have a bug in my C code. Here's what I expect to happen: [describe]. Here's what actually happens: [describe]. Here's the relevant code: [paste]. Walk me through how to debug this — don't just give me the fix, help me find it myself so I learn.
The "is my approach right?" prompt
I'm about to implement [feature] in my C game. My plan is: [describe your approach]. Before I write the code — is this a sound approach? Are there obvious problems I haven't considered? Don't write the code yet, just critique the plan.
Exercises  Prompt-to-Code — can you write the prompt that produces this? ▼
// How these work
Each exercise shows a target piece of game code. Your job: write the prompt that would make Claude Code produce it — without looking at the reference prompt first. The comments in the code map each line back to the keyword your prompt needs to contain. If your prompt is missing a keyword, the AI has to guess — and guessing is where wrong code comes from.

This is the real skill: not memorizing C, but knowing exactly what to specify so the AI builds your system, not its own invention. Write your prompt, then expand the reference to check what you missed.
Exercise 1 — A simple function (Phase 3 knowledge)
Target output. The comments point to the prompt keywords you must include:
// KEYWORD: "function named player_heal"  → names the function
// KEYWORD: "returns nothing / void"       → fixes the return type
// KEYWORD: "takes a Player pointer and an int amount" → exact params
void player_heal(Player* p, int amount) {
    p->health += amount;        // KEYWORD: "add amount to health"
    if (p->health > 100)         // KEYWORD: "cap at 100" → the upper bound
        p->health = 100;
}
▸ Reveal a reference prompt — check what you missed ▼
I have a Player struct in C with fields: float x, float y, int health, bool alive. Write a function named player_heal that returns void and takes a Player pointer and an int amount. It should add amount to the player's health, then cap health at 100. Don't write any other functions — just this one. Match my existing player.c style.
Notice what the prompt locks down: the name, the return type, the exact parameters, the behavior, the cap, and the scope ("just this one"). Leave any of these out and the AI invents them — maybe it returns the new health, maybe it caps at 99, maybe it adds three more helper functions. Specification is control.
Exercise 2 — A struct you designed (Phase 3.5 knowledge)
Target output — an Enemy struct. The AI should produce exactly these fields, no extras:
// KEYWORD: "enum for enemy type, melee or ranged" → the EnemyType enum
typedef enum { ENEMY_MELEE, ENEMY_RANGED } EnemyType;

// KEYWORD: "struct named Enemy"          → names the struct
typedef struct {
    float     x, y;     // KEYWORD: "float position"   → use float for x/y
    int       health;   // KEYWORD: "int health"       → whole number
    EnemyType type;     // KEYWORD: "a type field"     → reuse the enum above
    bool      alive;    // KEYWORD: "alive flag"       → bool, not int
} Enemy;
// KEYWORD: "fields only, no functions, no extras" → stops scope creep
▸ Reveal a reference prompt — check what you missed ▼
I'm building a 2D game in C. Define a struct named Enemy with: a float position (x and y), an int health, a type field that is an enum of melee or ranged, and a bool alive flag. Give me the enum and the struct only — no functions, no extra fields I didn't ask for. I'll write the rest myself.
The trap here is scope creep. Ask vaguely for "an enemy system" and you'll get spawn functions, AI behavior, a render call — none of which match what you've built. Specifying "fields only, no functions" keeps the architecture yours.
Exercise 3 — A surgical edit (Phase 5 knowledge)
Target output — only the lines to ADD inside an existing WM_KEYDOWN block. Not a rewrite:
// KEYWORD: "add WASD alongside existing arrow keys" → adds, doesn't replace
// KEYWORD: "inside the WM_KEYDOWN case"  → exact location
if (wp == 'A') g_x -= 5;   // KEYWORD: "move left"
if (wp == 'D') g_x += 5;   // KEYWORD: "move right"
if (wp == 'W') g_y -= 5;   // KEYWORD: "move up"
if (wp == 'S') g_y += 5;   // KEYWORD: "move down"
// KEYWORD: "don't rewrite my file, show only lines to add" → surgical scope
▸ Reveal a reference prompt — check what you missed ▼
I have a working Win32 window in C that moves a rectangle with arrow keys using g_x and g_y, handled inside a WM_KEYDOWN case. Add WASD movement alongside the existing arrow keys — A/D move left/right by 5, W/S move up/down by 5. Show me ONLY the lines to add and where they go. Don't rewrite my file, don't add new functions, don't change the structure.
The two critical phrases: "alongside the existing" (so it adds, not replaces) and "show me ONLY the lines to add, don't rewrite my file" (so you get a small reviewable diff instead of a regenerated file you have to re-read entirely). As systems grow, surgical scope is what keeps AI safe to use.
Exercise 4 — A system that fits your codebase (Phase 6 knowledge)
Target output — a game_update that uses YOUR existing struct and functions, in your style:
// KEYWORD: "switch on the current state"  → the state-machine shape
void game_update(Game* g) {
    switch (g->state) {       // KEYWORD: "Game struct has a state field"
        case STATE_PLAYING:    // KEYWORD: "only update when PLAYING"
            player_move(&g->player, g->input_dx, 0);
            // KEYWORD: "call my existing player_move" → reuse, don't reinvent
            if (!g->player.alive)   // KEYWORD: "when player not alive"
                g->state = STATE_GAME_OVER; // KEYWORD: "transition to GAME_OVER"
            break;
        case STATE_MENU: case STATE_GAME_OVER: break;
    }
}
// KEYWORD: "match my style, no new dependencies" → fits the codebase
▸ Reveal a reference prompt — check what you missed ▼
Here is my game's context. Game struct: { GameState state; Player player; int input_dx; }. GameState enum: MENU, PLAYING, GAME_OVER. I already have a function player_move(Player* p, float dx, float dy) and player has a bool alive field. Write ONLY game_update(Game* g) that switches on the current state, and when PLAYING calls my existing player_move using input_dx, then transitions to GAME_OVER if the player is not alive. Match my snake_case style. No new dependencies, no new files.
This is the Phase 6 lesson in one prompt: you paste the context (struct, enum, existing functions) first, then ask for the implementation. Without that context block the AI invents its own struct, its own move function, its own state names — and nothing connects to what you and your partner already built.
// The anti-pattern these exercises train you to avoid
Every one of these exercises is really teaching the same thing: the gap between what you specify and what you leave unspecified is where wrong code is born. The AI fills every gap with a guess. A guess that compiles and runs looks correct — until it silently doesn't match your architecture, your types, or your partner's code.

If you can write a prompt that reproduces the target exactly, you understand the system well enough to verify anything the AI hands back. That is the actual goal of this whole roadmap: not to write every line yourself, but to know enough to direct and verify.
