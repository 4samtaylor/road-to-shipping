Build Spec  Write the requirements before you build ▼
Three requirements per build, written before you open the editor. Each line is something you can test: run the program and answer yes or no. Tick the build when all three pass.

damage.c: it should:

  • read an attack, a defence (0 to 100) and a crit multiplier typed on one line, such as 40 25 1.5, with a single scanf, and print read 3 values

Starter Code  damage.c ▼
damage.c, your first calculator 
#define _CRT_SECURE_NO_WARNINGS
#include <stdio.h>

#define ENEMY_HP 100

int main(void) {
    int attack, defence, base, damage, got;
    int hp = ENEMY_HP;
    float crit;

    printf("Attack, defence (0-100) and crit, e.g. 40 25 1.5: ");
    got = scanf("%d %d %f", &attack, &defence, &crit);
    printf("read %d values\n", got);

    // TODO 1: base damage is the attack, reduced by defence percent.
    //         Multiply before you divide, or 75 / 100 gives 0.
    base = attack;

    // TODO 2: apply the crit. base * crit is a float, so cast it
    //         back to int on purpose: 40 25 1.5 should give 45.
    damage = base;

    // TODO 3: take damage off hp with -=, then print every value in
    //         lined-up columns, like:  ATK   40 | DEF  25% | CRIT x1.50 | DMG   45 | HP   55
    printf("ATK %d | DMG %d | HP %d\n", attack, damage, hp);

    return 0;
}
Predict the Output  4 drills, guess first, then run it ▼
// Four classic traps
Every one compiles clean and runs fine, so nothing warns you. Prediction on paper first, then run.
1. Truncation: the C4244 from session 1, on purpose this time
#include <stdio.h>

int main(void) {
    float x = 1.8f;
    int   n = (int)x;

    printf("%d\n", n);
    printf("%.1f\n", x);
    printf("%d\n", (int)9.99f);
    return 0;
}
Write your prediction down, then compile and run it.
Reveal answer 
1
1.8
9
float to int truncates toward zero. It does not round. 1.8 becomes 1 and 9.99 becomes 9. The fraction is thrown in the bin, not weighed up.

This is exactly what int var(float x) { return x; } was doing silently in session 1, and why the compiler raised C4244. Note that x itself is untouched, it still prints 1.8. The (int) cast doesn't change the behaviour one bit; it changes the conversation with the compiler from "you might not have meant this" to "I meant it."
2. A char is a number wearing a costume
#include <stdio.h>

int main(void) {
    char c = 'A';

    printf("%c %d\n", c, c);
    c = (char)(c + 2);
    printf("%c %d\n", c, c);
    printf("%d\n", 'a' - 'A');
    return 0;
}
Write your prediction down, then compile and run it.
Reveal answer 
A 65
C 67
32
A char is a one-byte integer holding an ASCII code. 'A' is 65. Add 2 and you have 67, which %c shows as C and %d shows as 67, same byte, two ways of looking at it. The specifier decides what you see, not the data.

The (char) cast is there because c + 2 is an int, and putting an int back in a char box is the same narrowing that produced C4244 in session 1. And 'a' - 'A' being exactly 32 is the whole trick behind flipping letter case by hand.
3. += and ++ in the same line
#include <stdio.h>

int main(void) {
    int combo = 2;
    int score = 10;

    score += combo * 3;
    printf("%d\n", score);
    score = combo++ * 10;
    printf("%d %d\n", score, combo);
    score -= ++combo + 1;
    printf("%d %d\n", score, combo);
    return 0;
}
Write your prediction down, then compile and run it.
Reveal answer 
16
20 3
15 4
+= works out the whole right side first: combo * 3 is 6, so score goes from 10 to 16. It never means (score + combo) * 3.

combo++ is postfix, so the multiply gets the old value: 2 times 10 is 20, and only then does combo become 3. On the last line ++combo is prefix: combo becomes 4 first, plus 1 is 5, and 20 minus 5 is 15. ++ binds tighter than * and +, so it always sticks to its own variable.

Each line changes combo once and reads it only in that one place, which is why the answer is certain. Write combo++ * combo and there is no right answer at all.
4. Big numbers on Windows
#include <stdio.h>

int main(void) {
    long long xp = 2000000000LL;
    unsigned int lives = 1;

    printf("%zu %zu\n", sizeof(long), sizeof(long long));
    xp += xp;
    printf("%lld\n", xp);
    lives -= 2;
    printf("%u\n", lives);
    return 0;
}
Write your prediction down, then compile and run it.
Reveal answer 
4 8
4000000000
4294967295
On Windows a long is 4 bytes, the same as an int, even in a 64-bit program. On Linux and Mac it’s 8, which is why code from there sometimes breaks here. 4 billion doesn’t fit in 4 bytes, so xp has to be a long long.

lives is unsigned, so 1 minus 2 can’t be -1. It wraps round to the top, UINT_MAX. That’s defined, and it’s exactly why game values like lives should stay plain int.

Had xp been an int, adding past 2147483647 would be signed overflow: undefined behaviour, not a neat wrap.
Quiz Yourself  3 questions, answer out loud before revealing ▼
1. Why is there a space in scanf(" %c", &input)?
Reveal answer
The space tells scanf to skip over any leftover whitespace first, including the Enter key still sitting in the input buffer from the previous read. Without it, scanf grabs that newline as your character and the loop appears to skip a turn. And the & hands scanf the address of your variable so it can write into it, rather than a copy of its value.
2. A health bar is drawn from health / max_health, both ints. It stays empty until health is full. Why, and what are two ways to fix it?
Reveal answer
Int divided by int is an int, so 60 / 100 is 0. Cast one side before the division: (float)health / max_health. Or multiply first: health * 100 / max_health gives a whole-number percentage. Casting after, as in (float)(health / max_health), is too late.
3. Your frame counter is an int and the game runs at 60 frames a second. Roughly how long until it overflows, and what type would you switch to if that mattered?
Reveal answer
INT_MAX is 2147483647. At 60 a second that’s about 35.8 million seconds, roughly 414 days, so an int is fine for one session. Past that it’s signed overflow, which is undefined behaviour, not a tidy wrap. Switch to long long and print it with %lld. Not long: on Windows that’s still 4 bytes.
Mixed Review  two from Phase 01 ▼
Two questions from earlier phases. Remembering something after a gap is what makes it stay, answer out loud first.
1. [Phase 01] What does printf("%d%%\n", 50); print?
Reveal answer
50%. %d is replaced by 50, and %% is printf's way of printing one percent sign, a single % would start another format specifier.
2. [Phase 01] build says BUILD FAILED, you run game.exe anyway and it works perfectly. What did you just run?
Reveal answer
The .exe from your last successful build. A failed compile doesn't delete the old file, it just doesn't replace it. That's why build.bat exits as soon as %ERRORLEVEL% isn't 0, so you notice before you test old code.

Stuck & Curious  Common errors at this stage ▼
scanf seems to skip input or read the wrong character
The space before %c in scanf(" %c", &input) is intentional. It eats the leftover newline from pressing Enter. Without it, scanf captures Enter instead of your character. One of the most famous C beginner traps, remember it forever.
