Explain Like I'm New  Structs, in plain English ▼
// A struct is a form with named boxes
An array is many boxes of the same type, reached by number. A struct is a few boxes of different types, reached by name. A player has a position (two floats), health (an int) and whether it's alive (a bool). Those four things belong together — without a struct you'd pass four loose variables to every function and hope you never mix up whose x is whose. 
#include <stdbool.h>   // gives you bool, true and false

typedef struct {
    float x;
    float y;
    int   health;
    bool  alive;
} Player;             // typedef: from now on this shape is called Player

Player hero;           // one player, built from the blueprint
hero.health = 100;     // the dot reaches into one named box
The struct definition is a blueprint. It doesn't create a player — Player hero; does. You can build as many as you like from one blueprint.
typedef is what lets you write Player on its own, like int or float. Without it you'd write struct Player every time.
// Phase 3's arrays + this phase's structs = every game object list
Put the two together and you get the shape nearly every game runs on:
Enemy enemies[MAX_ENEMIES];

for (i = 0; i < MAX_ENEMIES; i++) {
    if (enemies[i].alive) {
        enemies[i].x -= 1.0f;     // one array, one loop, one struct per thing on screen
    }
}
Phase 6 is built out of exactly this. The stretch goal at the end of this phase is your first go at it.
// A struct is a value — copying it copies everything
b = a; copies every field, and from then on they're two separate players. The same thing happens when you pass a struct to a function: the function gets its own copy. That's usually not what a game wants — when the enemy hits the player, you want the real player's health to drop. Pointers are how you hand over the real thing. That's the next section.
Explain Like I'm New  Pointers, in plain English ▼
// Memory is a street of numbered houses
Every variable in your program lives somewhere in memory — like a house on a street, each with its own address. A pointer is just a piece of paper with a house's address written on it. 
int x = 5;        // a house with the number 5 inside it
int* p = &x;     // p is a paper holding x's address
printf("%d", *p); // *p = "go to that address, look inside" → 5
&x — "the address of x." The & gives you the house's location, not what's inside.
*p — "go to the address p holds and look inside." This is called dereferencing.
A pointer doesn't hold the value — it holds where the value lives.
// Why games pass pointers — the photocopy problem
When you hand a function a normal value, C makes a photocopy. The function scribbles on the copy — your original is untouched. 
// WITHOUT a pointer — works on a photocopy
void move(Player p) { p.x += 5; }  // changes the copy, not the real player

// WITH a pointer — works on the real thing
void move(Player* p) { p->x += 5; } // reaches the real player by address
Passing Player p is like giving someone a photocopy of your house plans — they can scribble on it but your house doesn't change. Passing Player* p is like giving them your address — now they can walk in and actually move your furniture. Every game function that changes an object takes a pointer.
// The arrow vs the dot — one simple rule
p->health is just shorthand for "go to the address, then grab the health field." You'll see it everywhere in game code. The rule is dead simple:

Pointer? Use the arrow →  p->health
Actual value? Use the dot .  player.health

Starter Code  player.h + player.c ▼
player.h — the declaration (what exists) 
#pragma once
#include <stdbool.h>

// A struct groups related data together
// Think of it as a blueprint for a game object
typedef struct {
    float x;
    float y;
    int   health;
    bool  alive;
} Player;

// Function declarations — the "what" without the "how"
Player player_create(float start_x, float start_y);
void   player_move(Player* p, float dx, float dy);
void   player_take_damage(Player* p, int amount);
void   player_print(Player* p);
player.c — the definitions (the actual code) 
#include "player.h"
#include <stdio.h>

Player player_create(float start_x, float start_y) {
    Player p;
    p.x      = start_x;
    p.y      = start_y;
    p.health = 100;
    p.alive  = true;
    return p;
}

// Player* means "a pointer to a Player" — we pass by pointer
// so the function can MODIFY the original, not a copy
void player_move(Player* p, float dx, float dy) {
    p->x += dx;
    p->y += dy;
}

void player_take_damage(Player* p, int amount) {
    p->health -= amount;
    if (p->health <= 0) {
        p->health = 0;
        p->alive = false;
    }
}

void player_print(Player* p) {
    printf("Player pos: (%.1f, %.1f) health: %d alive: %s\n",
           p->x, p->y, p->health,
           p->alive ? "yes" : "no");
}

Tooling  The Debugger — watch a pointer change live ▼
// Why printf debugging runs out of road
Printing values has worked fine so far because your programs are twenty lines long. It stops working the moment there's a loop running sixty times a second, a struct with six fields, and a function three calls deep.

You end up adding a printf, rebuilding, running, reading, deleting the printf, adding another one somewhere else. Every cycle costs a build. And a printf only shows you what you thought to ask for — it can't show you the thing you didn't suspect.
A debugger freezes the program mid-run and lets you look at everything at once. No rebuild, no guessing which variable to print. You already paid for this — it just isn't switched on yet.
// You already did the hard part in session 1
Your build.bat has /Zi in it. That flag tells cl to write a PDB — a symbol file, game.pdb, sitting right next to game.exe. It's the map that says "this machine instruction came from line 42 of player.c, and the thing in that register is called p."

Without it a debugger sees a wall of assembly. With it, you get your own source code with a yellow arrow on the current line. The linker line you saw in session 1 — /debug /out:game.exe — is the other half of the same setup. Nothing to install. One config file and you're in.
// Setting it up — four steps, once, forever
1
In VS Code, install the C/C++ extension from Microsoft (ms-vscode.cpptools). That's what provides the cppvsdbg debug type — the one that speaks MSVC and PDB.
2
Open your repo as a folder (File → Open Folder), not as a single file. ${workspaceFolder} only means something if VS Code has a folder open.
3
Create .vscode/launch.json in the repo root and paste the config below. Commit it — your partner gets debugging for free.
4
Run build first, every single time. F5 launches the exe that's on disk. It does not compile for you. This is the number one reason breakpoints "don't work."
.vscode/launch.json — minimal MSVC config 
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Debug game.exe",
      "type": "cppvsdbg",
      "request": "launch",
      "program": "${workspaceFolder}/game.exe",
      "args": [],
      "stopAtEntry": false,
      "cwd": "${workspaceFolder}",
      "environment": [],
      "console": "integratedTerminal"
    }
  ]
}
// Four keys and one panel. That's the whole debugger.

What it does

F5
Start debugging. Also "keep going" once you're stopped — runs until the next breakpoint.

The Watch panel is the point of the whole exercise. Type any expression into it — p, *p, p->health, hero.x — and it re-evaluates after every step. You can also just hover a variable in the editor while stopped.

2

4

Look at them before you step. p is a number like 0x00affc10 — that's the address, the piece of paper with the house number on it. *p expands into the whole Player. p->health is one field inside it.
6

7

Do the same thing with the broken version from session G — player_move(Player p, ...), no asterisk. Watch p.x change inside the function, then step out and watch hero.x sit there untouched. The copy dying at the closing brace, on screen.
My breakpoints are hollow circles — "the breakpoint will not currently be hit, no symbols have been loaded"
Three causes, in the order they actually happen.

1. Stale exe. You edited the .c file and hit F5 without running build. VS Code launches whatever game.exe is on disk — it has no idea your source changed, and the line numbers in the old PDB no longer match your editor. Run build, then F5. Make it muscle memory.

2. No PDB. Check /Zi is still in build.bat and that game.pdb exists next to game.exe. If you cleaned the folder, or your .gitignore rules led you to delete it, there are no symbols to load. Rebuild.

3. Wrong program path. "program" must point at the exe your build.bat actually produces. If build.bat says /Fe:game.exe in the repo root, ${workspaceFolder}/game.exe is right. If you build into a subfolder, the path has to say so. And if you opened a single file instead of the folder, ${workspaceFolder} isn't your repo at all.
F11 jumped me into a screenful of assembly I didn't write
You stepped into a library function — printf, scanf, strlen. Those come from the C runtime and you don't have their source, so the debugger shows you the disassembly. Press Shift+F11 to step back out, and use F10 on lines that call library functions. F11 is for stepping into functions you wrote.
Stuck & Curious  Pointers and structs specifically ▼
What is a pointer actually?
Every variable lives at a memory address. A pointer stores that address. int x = 5 stores the value 5. int* p = &x stores the address of x. *p reads what's at that address (5). We use pointers in game functions so the function modifies the original object, not a copy. Think of it as giving someone your house address vs handing them a copy of everything in it.
Why use Player* instead of Player in function parameters?
When you pass Player (no asterisk), C copies the entire struct. Changes inside the function don't affect the original. When you pass Player* (pointer), you pass the address — the function can reach back through it and modify the real player. Every game function that changes an object passes a pointer.
Why use -> instead of . when using a pointer to a struct?
p->health is shorthand for (*p).health. Simple rule: pointer = arrow (->), value = dot (.). When you have Player* p, use p->health. When you have Player p directly, use p.health.
Linker error: "unresolved external symbol player_move"
You declared the function in player.h but the compiler can't find the definition. You're probably only compiling main.c. Compile both files: cl main.c player.c. Both need to be listed.
What's the difference between player.h and player.c?
The .h file (header) contains declarations — "these things exist." The .c file contains definitions — "here's how they work." Other files #include the .h to know what's available without reading the implementation. This lets you and your partner work on separate files independently.
// Curious — the "why" questions
Why did insert_score change my real array in Phase 3, when hurt_copy can't change hero?
Because C never copies an array into a function. When you pass scores, what actually travels is the address of its first box — a pointer, without the asterisk on show. So insert_score was reaching into your real array all along. A struct is different: pass one without a * and the whole thing is copied. Same language, two rules, and now you know both.
What is NULL?
A pointer that points nowhere — address zero, on purpose. Functions use it to say "I couldn't give you one": fopen returns NULL when the file isn't there. Following a NULL pointer (p->health when p is NULL) crashes the program on the spot, which is actually the good outcome — it fails loudly, right where the bug is. Check before you use: if (p != NULL).
GDScript has no pointers. Why does C make me deal with them?
GDScript has them — it just hides them. Every object in Godot is passed by reference, which is a pointer with the asterisk filed off. C makes you choose, and shows you the cost of each choice: copying a 6-field struct every frame versus handing over one address. Once you've seen that, you'll understand why Godot behaves the way it does when you pass a node to a function.
Claude Code Prompts  Phase 3.5 ▼
// This phase is where AI prompting gets architectural
Functions and structs are the building blocks of game systems. When you ask AI to write a function, you are making an architectural decision — what it's named, what it takes in, what it returns, what it does to the data. If you don't specify these things, AI will invent them. And its invented architecture may not match your game.

The skill to develop here: design the interface first (the function signature), then ask AI to implement the body. You own the shape. AI fills in the detail.

✗ Bad — you've given up control
"Write a player system for my game"
AI will invent the struct fields, function names, file structure, and architecture. None of it will match what you build in Phase 5. You'll be refactoring it constantly.

AI implements exactly what you specified. The struct is yours. The function signature is yours. AI wrote the 3 lines inside.

Before asking AI to write any function, write the declaration yourself first:

Predict the Output  4 drills — guess first, then run it ▼
// Run these in the debugger the second time
Predict on paper, run, compare. Then go back through drills 1 and 3 with a breakpoint and the Watch panel open — these are short enough to step through line by line, and seeing the copy die at the closing brace does more than any explanation on this page.
1. Copy versus pointer — the same function twice
#include <stdio.h>

typedef struct {
    int health;
} Player;

void hurt_copy(Player p)  { p.health -= 10; }
void hurt_real(Player* p) { p->health -= 10; }

int main(void) {
    Player hero;
    hero.health = 100;

    hurt_copy(hero);
    printf("after hurt_copy: %d\n", hero.health);

    hurt_real(&hero);
    printf("after hurt_real: %d\n", hero.health);
    return 0;
}
Write your prediction down, then compile and run it.
Reveal answer 
after hurt_copy: 100
after hurt_real: 90
hurt_copy ran. It subtracted 10. It worked perfectly — on a photocopy of hero that C created for the call and destroyed at the closing brace. No warning, no error, no effect.

hurt_real got the address instead, reached back through it, and changed the real thing. This is the single most important behaviour in the phase, and the reason every function in player.c takes a Player*.
2. What does b = a do to a struct?
#include <stdio.h>

typedef struct {
    int   health;
    float x;
} Player;

int main(void) {
    Player a;
    Player b;

    a.health = 100;
    a.x      = 5.0f;

    b = a;
    b.health = 1;

    printf("a.health %d  b.health %d\n", a.health, b.health);
    printf("a.x %.1f  b.x %.1f\n", a.x, b.x);
    return 0;
}
Write your prediction down, then compile and run it.
Reveal answer 
a.health 100  b.health 1
a.x 5.0  b.x 5.0
One short line copied every byte. From that moment a and b are two separate Players that happen to have started out identical — changing one cannot touch the other.

Hold on to this one. In C, a struct is a value. In GDScript, which is where your actual game gets built, objects are references — the same two lines would give you two names for one object, and setting b.health would change a.health too. See the C → Godot handoff section at the bottom of this page.
3. Three spellings, one box
#include <stdio.h>

typedef struct {
    int health;
} Player;

int main(void) {
    Player  hero;
    Player* p = &hero;

    hero.health = 100;
    p->health   -= 30;
    (*p).health -= 20;

    printf("%d %d\n", hero.health, p->health);
    return 0;
}
Write your prediction down, then compile and run it.
Reveal answer
50 50

p->health is nothing more than shorthand for (*p).health. Both mean "go to the address, then take the health field." And hero.health is that same field reached the direct way.

Three spellings, one box in memory. The two printed numbers are identical because there is only one Player in this entire program — p is a note with hero's address written on it, not a second player.
4. Truncation, now living inside a struct
#include <stdio.h>

typedef struct {
    float x;
    int   steps;
} Player;

int main(void) {
    Player hero;
    hero.x     = 0.0f;
    hero.steps = 0;

    hero.x     += 2.7f;
    hero.steps += (int)2.7f;

    printf("x %.1f  steps %d\n", hero.x, hero.steps);
    printf("%d\n", (int)(hero.x * 2.0f));
    return 0;
}
Write your prediction down, then compile and run it.
Reveal answer 
x 2.7  steps 2
5
The float field keeps its fraction. The int field throws it away — truncated toward zero, so 2.7 adds 2 and 5.4 comes out 5. Session 1's C4244 lesson, now happening one field away from another field that behaves differently.

The game bug: keep a position as an int and every fractional movement is lost, so a player moving 2.7 per frame actually moves 2 and drifts further behind the truth every frame. Positions stay float. You truncate once, at the moment you draw, and never store the result back.
Quiz Yourself  5 questions — answer out loud before revealing ▼
1. void move(Player p) and void move(Player* p) — only one of them actually moves your player. Which, and why?
Reveal answer
The pointer version. Without the asterisk, C hands the function a full photocopy of the struct — it edits the copy, the copy is thrown away when the function ends, and your real player never moved. With Player* you're handing over the address, so the function reaches back into the original.
2. What is p->health shorthand for, and when would you write p.health instead?
Reveal answer
p->health is shorthand for (*p).health — go to the address, then grab the field. Use the arrow when you're holding a pointer. Use the dot when you're holding the actual struct: Player player; player.health. Pointer = arrow, value = dot.
3. In one sentence each: what does &x give you, and what does *p give you?
Reveal answer
&x gives the address where x lives — the house number, not what's inside. *p goes to the address p is holding and reads what's there. Same & you were already using in scanf(" %c", &input) back in Phase 2 — you were handing scanf an address the whole time.
4. The build says unresolved external symbol player_move. What did you forget?
Reveal answer
To compile player.c. The declaration in player.h told the compiler the function exists, so compiling succeeded — but the linker then went looking for the actual body and found nothing. Fix: cl main.c player.c, or add player.c to the set SOURCES= line in your build.bat. Compiler error vs linker error is a real distinction: one means "I don't understand this," the other means "I can't find this."
5. What belongs in player.h and what belongs in player.c?
Reveal answer
The .h holds declarations — the struct definition and the function signatures. It's the "what exists" list that other files include. The .c holds the definitions — the actual bodies. That split is what lets you and your partner work in separate files without reading each other's implementations, and it's the reason a header change forces a rebuild while a .c change doesn't.

Mixed Review  one from Phase 02, one from Phase 03 ▼
Two questions from earlier phases. Remembering something after a gap is what makes it stay — answer out loud first.
1. [Phase 03] What's wrong with #define MAX_SCORES 5;?
Reveal answer
The semicolon. #define is find-and-replace, so every MAX_SCORES becomes 5; — and int scores[MAX_SCORES]; turns into int scores[5;];. The error points at the array line, not the define, which is what makes it nasty.
2. [Phase 02] What do 7 % 3 and -7 / 2 give you in C?

1 and -3. Integer division truncates toward zero, so -3.5 becomes -3, not -4. Same rule as casting a float to an int — it chops, it never rounds.
