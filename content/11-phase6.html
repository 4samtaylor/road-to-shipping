Explain Like I'm New  The game loop & state machine, in plain English ▼
// The game loop is a flipbook
A game isn't one picture — it's a flipbook drawn 60 times a second. Each page (frame) the game does the same three things, then flips to the next page. That's the entire heartbeat of every game ever made: 
while (game_running) {
    handle_input();  // 1. What did the player just press?
    update();        // 2. Move everything, check collisions, apply rules
    render();        // 3. Draw the current picture to the screen
}                    // then loop — draw the next page of the flipbook
Input → Update → Render, 60 times a second. The player's brain fills in the motion between pages, exactly like a flipbook. Keep these three as separate functions — when something breaks, you'll know whether it's an input bug, a logic bug, or a drawing bug.
// A state machine is a TV with channels
Your game is never doing everything at once. At any moment it's on exactly one channel: the menu, the gameplay, the pause screen, or game over. A state machine is just a variable that remembers which channel you're on, plus the rules for changing channels. 
typedef enum { STATE_MENU, STATE_PLAYING, STATE_GAME_OVER } GameState;

// In update(), you check the channel and act accordingly:
switch (game->state) {
    case STATE_MENU:      /* wait for Start */ break;
    case STATE_PLAYING:   /* run the actual game */ break;
    case STATE_GAME_OVER: /* show score, wait for restart */ break;
}
Without this, you end up with if (inMenu) and if (isPlaying) scattered through your whole codebase, fighting each other. With a state machine, each channel handles itself cleanly and you change channels by changing one variable.
// AABB collision — do two boxes overlap?
AABB stands for Axis-Aligned Bounding Box — fancy words for "two rectangles that aren't rotated." The question "did the bullet hit the enemy?" is really "do these two boxes overlap?" Picture two windows on a wall: they overlap only if neither one is fully to the left, right, above, or below the other. 
// Returns true if box A and box B overlap
a.x < b.x + b.w &&  // A's left edge is left of B's right edge
a.x + a.w > b.x &&  // A's right edge is right of B's left edge
a.y < b.y + b.h &&  // A's top is above B's bottom
a.y + a.h > b.y     // A's bottom is below B's top
Four comparisons. If all four are true, the boxes overlap and you've got a hit. This one function handles the player touching pickups, bullets hitting enemies, and the player landing on platforms — the bulk of 2D collision in your runner.
// How it all fits together — one frame, start to finish
One frame begins (1/60th of a second)
  → handle_input(): player pressed Right → remember that
  → update():
      → check state — we're PLAYING
      → player_move(&player, 5, 0)  (uses the pointer from Phase 3.5)
      → for each enemy: did AABB overlap the player? → take damage
      → if player.alive is false → switch state to GAME_OVER
  → render(): draw the player and enemies at their new spots
Frame ends → loop → next frame
Every concept from Phases 1–5 shows up here: the loop (Phase 2), the Player struct and pointers (Phase 3.5), the window and input (Phase 5). This phase is where it all connects.

Starter Code  game_state.h ▼
game_state.h — state machine pattern 
#pragma once

// All possible game states
typedef enum {
    STATE_MENU,
    STATE_PLAYING,
    STATE_PAUSED,
    STATE_GAME_OVER
} GameState;

// The whole game lives in this struct
typedef struct {
    GameState state;
    Player    player;
    int       score;
    float     delta_time; // seconds since last frame
} Game;

// AABB collision: do rectangles a and b overlap?
static inline int aabb_overlap(
    float ax, float ay, float aw, float ah,
    float bx, float by, float bw, float bh)
{
    return ax < bx+bw && ax+aw > bx &&
           ay < by+bh && ay+ah > by;
}

// Your game loop structure — call each every frame:
void game_init(Game* g);
void game_handle_input(Game* g);
void game_update(Game* g);
void game_render(Game* g);

Stuck & Curious  the prototype specifically ▼
My player moves faster on my PC than on my partner's
Your movement is per frame, not per second. x += 5; moves 5 pixels every frame, so a machine running at 144 fps moves more than twice as far as one at 60. Use the frame time from Phase 5: x += speed * dt; where speed is pixels per second and dt is the frame time in seconds. Now both machines move the same distance per second.
The player sinks into walls before the collision stops them
You're moving first and testing afterwards, then doing nothing about the overlap. The simplest fix: remember the old position, move, test, and if the boxes now overlap, put the player back where they were. It's not physics, but it's what plenty of shipped games do.
Something happens twice when the state changes
You changed state halfway through the update, and later code in the same frame ran with the new state. Either break straight out of the switch after changing state, or set a next_state variable and apply it at the very end of the frame.
// Curious — the "why" questions
Why test boxes (AABB) instead of the real shapes?
Speed and simplicity. Two axis-aligned boxes overlap if and only if they overlap on x and on y — four comparisons. Exact shapes can cost hundreds. Most games, Godot included, test the boxes first and only bother with exact shapes when the boxes say "maybe". Players almost never notice the corners.
Why keep update and render separate?
Because they change for different reasons. Pause the game and you stop calling update but keep calling render, so the screen still draws. Run physics at a fixed rate and you call update a fixed number of times while render runs as fast as it can. Godot gives you exactly this split as _physics_process and _process.
Why an enum for the state, not just an int?
An int works — the compiler turns the enum into ints anyway. But state = STATE_GAME_OVER says what it means and state = 2 doesn't, and the debugger's Watch panel shows the name too. When you add a PAUSED state in the middle of the list, nothing that uses the names breaks.

Mixed Review  one from Phase 4.5, one from Phase 05 ▼
Two questions from earlier phases. Remembering something after a gap is what makes it stay — answer out loud first.
1. [Phase 4.5] Why write the reset as one function and call it from both the start and the restart?
Reveal answer
So there's exactly one place that defines "a fresh game". With two copies, you'll add a new variable, reset it in one place and forget the other — and the bug only shows up on the second run. One function, one source of truth.
2. [Phase 05] Your movement code is x += 5; and the frame timer says 16 ms. How fast is the player moving, and what happens on a 144 Hz screen?
Reveal answer
About 300 pixels a second (5 × ~60 frames). On a machine running at 144 fps it's 720 pixels a second — more than twice as fast, from the same code. Multiply by the frame time instead: x += 300.0f * dt; gives 300 pixels a second everywhere.
