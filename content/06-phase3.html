Explain Like I'm New  Functions, in plain English ▼
// A function is a machine
A function is a machine: you put something in, it does something, and hands something back. Think of a vending machine. 
float var(float x) {
    return x;
}
float x — the slot you put money into (the input). float means it accepts decimals like 1.8.
float var(...) — the float at the front is what the machine spits out. Again, a decimal.
return x — "hand back whatever was put in." This machine just gives back exactly what you gave it.
So var(1.8) → puts 1.8 in → gets 1.8 back. A simple pass-through.
// printf is a fill-in-the-blank sentence
The % symbols are blank slots. The values after the comma fill them in: 
printf("I am %f years old\n", var(1.8));
//           ^^              ^^^^^^^
//        blank slot       fills this slot
%d — the slot expects a whole number (integer). 28, -5, 1000. No decimals.
%f — the slot expects a decimal number (float). 1.8, 3.14, -0.5.
Using the wrong one is like a form asking for your age in whole years, but you write 1.8 — the form gets confused. That's why an earlier bug printed 1: the code used %d, so 1.8 got chopped to 1.
// How var(1.8) becomes "I am 1.8 years old" — read inside-out
1. var(1.8) — put 1.8 into the vending machine, get 1.8 back
2. printf("I am %f years old\n", 1.8) — fill the %f slot with 1.8
3. Output: I am 1.800000 years old  (use %.1f to get 1.8 instead of 1.800000)
// Defining vs running — the recipe book
A program starts at main — but defining a function earlier in the file isn't "running" it, it's just describing the machine to the compiler beforehand. Think of a recipe book: writing the recipe for var (the machine exists, but isn't turned on yet) happens before main actually uses the recipe for the first time. The definition can sit at the top of the file; it only runs when something calls it.
// Two different returns — they are not the same
This is the key confusion. There are two separate functions, each with their own return:
var  |  main
Returns to...
caller (line 14)  |  the OS
Returns...
1.8 (result)  |  0 (success)
return x inside var → gives 1.8 back to the line that called it.
return 0 inside main → tells the OS "the program finished without errors."
They're completely separate. return 0 has nothing to do with 1.8.
// The full flow, in plain English
Program starts → enter main
  → reach the printf line
    → pause printf, call var(1.8)
      → var receives 1.8, returns 1.8, shuts down
    → printf gets 1.8 back, prints the sentence
  → reach return 0 → program exits, tells OS "all good"
// The big picture — every C program
#include     → borrow the toolbox (printf lives in stdio.h)
float var()  → define your own mini-machine
main()       → the "start here" — every C program begins in main
printf()     → use the toolbox to print to the screen
return 0     → tell the OS "I finished successfully"
Every C program is just: borrow tools → define machines → run main → done.
Explain Like I'm New  Arrays and strings, in plain English ▼
// An array is a row of numbered boxes
So far every variable has been one box holding one value. An array is a row of boxes, all the same type, sitting side by side in memory — and you reach into them by number. 
int scores[5] = { 40, 95, 12, 78, 63 };

  index:    0     1     2     3     4
          +----+-----+-----+-----+-----+
  value:  | 40 |  95 |  12 |  78 |  63 |
          +----+-----+-----+-----+-----+
The numbering starts at 0, not 1. Five boxes means indexes 0, 1, 2, 3, 4. The last index is always size minus one. This trips up every single beginner, forever, and it's why you'll write i < count and never i <= count.
scores[2] reads the third box. scores[2] = 50; writes to it. The number in the brackets can be a variable, which is the whole point — a for loop can walk the entire row.
// Why your game cannot exist without this
In Phase 3.5 you'll build one Player. A game needs many of something, and "many" always means an array.
In the game
The array behind it
10 enemies on screen, each updated every frame
Enemy enemies[10];
A bullet pool you reuse instead of allocating
Bullet bullets[64];
Top 5 high scores
int scores[5];
Which keys are held down this frame
bool keys[256];
The player's name on the score screen
char name[32];
Every one of these gets walked with the same for loop shape you learned in Phase 2. Learn the shape once, use it everywhere.
// C has no string type — a string is a char array that ends in '\0'
Other languages hand you a String and manage it for you. C does not. In C, text is just an array of char with one special rule: the text ends at the first '\0' byte. 
char name[6] = "Sam";

  index:     0     1     2     3      4     5
           +-----+-----+-----+------+-----+-----+
  value:   | 'S' | 'a' | 'm' | '\0' |  ?  |  ?  |
           +-----+-----+-----+------+-----+-----+
                              ^^^^
                     the terminator. printf stops here.
'\0' is the null terminator. It's a real byte with the numeric value 0 — not the character '0', which is 48. You already met it in Phase 2: char input = '\0'; in your frame loop meant "nothing in here yet."
%s does exactly one thing: start at the address it's given and print bytes until it hits a '\0'. No terminator means no stop signal, and it keeps printing whatever memory comes next.
Buffer size includes the terminator. char name[32] holds at most 31 typed characters plus the '\0'. Always budget for that last byte.
// The trap: C does not check the edges of your array
This is the part that catches everyone. int scores[5] has no box number 5 — but if you write scores[5] = 99; the compiler shrugs and does it, stamping over whatever variable happened to be sitting next in memory. 
int scores[5];
scores[5] = 99;   // off by one. Compiles. Runs. Corrupts something else.
printf("%d", scores[7]);  // prints whatever bytes live there. "Garbage."
There's no crash and no error message. The symptom shows up somewhere else entirely — a health value that changes on its own, a name that turns to mush. That's what people mean by "undefined behaviour."
/W4 catches some of it. When the index is a literal constant like scores[5], MSVC will usually warn (C6201 / C4789) and /WX turns that into a stopped build — which is exactly why you turned those flags on in session 1. But when the index is a variable it cannot know, and it will not warn. The bounds are your job.
The habit to build now: every loop over an array is for (i = 0; i < count; i++). Every time. Don't improvise the condition.
Concepts First  #define — give your magic numbers a name ▼
// A magic number is a number with no name
Look at for (i = 0; i < 5; i++). Five what? Scores? Lives? Enemies? Now imagine that 5 appears in eleven places and you decide you want a top 10. You'll change nine of them and lose an evening finding the other two. #define gives the number a name, once, at the top of the file. 
#define MAX_SCORES 5      // no = sign, no semicolon
#define NAME_LEN   32
#define START_HP   100

int  scores[MAX_SCORES];
char names[MAX_SCORES][NAME_LEN];
for (i = 0; i < MAX_SCORES; i++) { ... }
Change MAX_SCORES to 10 and every array, every loop and every check follows. One edit, nothing to hunt for.
ALL_CAPS names are a convention, not a rule — but follow it. When you see capitals you know it's a fixed value, not a variable that can change while the game runs.
// It's find-and-replace, not a variable
Before the compiler proper sees your code, a step called the preprocessor goes through the file and swaps every MAX_SCORES for the text 5. That's all #define is. Two things follow from that:
No semicolon. #define MAX_SCORES 5; pastes 5; everywhere, so int scores[MAX_SCORES]; becomes int scores[5;]; — and the error points at a line that looks perfectly fine.
Brackets around anything with an operator. With #define WIDTH 80 + 2, the expression WIDTH * 2 becomes 80 + 2 * 2, which is 84, not 164. Write #define WIDTH (80 + 2).
You've used the preprocessor since Hello World: #include is the same step, pasting a whole header file in where the line was.

Starter Code  arrays.c — every line explained ▼
arrays.c — add it to build.bat, then run build 
#include <stdio.h>
#include <string.h>   // strlen, strcmp and strcspn all live in this toolbox

#define NAME_LEN 32   // how many chars the buffer holds, INCLUDING the '\0'
                     // #define is a find-and-replace done before compiling.

int main(void) {
    // An array is a row of numbered boxes, all the same type.
    int  scores[5] = { 40, 95, 12, 78, 63 };
    char name[NAME_LEN];   // 32 char boxes. Right now they hold garbage.
    int  count;
    int  max;
    int  i;

    // sizeof(the whole array) / sizeof(one box) = how many boxes.
    // sizeof hands back a size_t, so cast it — same move as (int)x in session 1.
    count = (int)(sizeof(scores) / sizeof(scores[0]));

    // Boxes are numbered from 0, so the last one is count - 1.
    // i < count, never i <= count. scores[5] does not exist.
    for (i = 0; i < count; i++) {
        printf("scores[%d] = %d\n", i, scores[i]);
    }

    // Assume box 0 wins, then let every other box challenge it.
    max = scores[0];
    for (i = 1; i < count; i++) {   // starts at 1 — 0 is already the champion
        if (scores[i] > max) {
            max = scores[i];
        }
    }
    printf("Highest: %d\n", max);

    // TODO 1: copy that loop and turn it into a min loop. Watch the > vs <.

    // A C string is just a char array that ends with a '\0'.
    // fgets reads at most NAME_LEN - 1 chars and writes the '\0' itself,
    // so it can never run off the end of the buffer. scanf("%s") can.
    printf("What's your name? ");
    if (fgets(name, NAME_LEN, stdin) != NULL) {
        // fgets keeps the Enter key as a '\n' on the end. Chop it off by
        // writing a '\0' over it — strcspn finds where the '\n' is.
        name[strcspn(name, "\n")] = '\0';
    } else {
        name[0] = '\0';   // read failed — make it an empty string, not garbage
    }

    // strlen counts characters up to the '\0'. It does NOT count the '\0'.
    // It returns a size_t, so cast it to keep %d honest under /W4 /WX.
    printf("Hi %s. That is %d characters.\n", name, (int)strlen(name));

    // strcmp returns 0 when the two strings are EQUAL. Read that twice.
    if (strcmp(name, "Sam") == 0) {
        printf("Good name.\n");
    }

    // TODO 2: print the name one char at a time with a for loop and %c.
    // TODO 3: printf("%d\n", name[0]); — why does that print a number?
    // TODO 4: print strcmp(name, "Sam") directly with %d for a match and a
    //         mismatch. Three different answers. Work out what they mean.

    return 0;
}
// Why fgets and not scanf("%s")
scanf("%s", name) has no idea how big your buffer is. Type 50 characters into a 32-byte buffer and it writes all 50 — straight past the end, over whatever was next. That's the classic buffer overflow, and MSVC dislikes it enough to reject scanf outright with C4996 under your current flags.

fgets(name, NAME_LEN, stdin) is told the size up front and refuses to write past it. It also reads the whole line including spaces, where %s stops dead at the first space — so "Sam Taylor" becomes "Sam". The only cost is the trailing newline, and one strcspn line removes it.
// The high-score build — the shape of it, not the answer
Five ints, sorted highest first. A new score arrives. Walk the array to find the first slot the new score beats. Everything from that slot down shifts one place toward the end — and the last one falls off. Then drop the new score into the hole.

The trick is the direction you shift. If you copy forwards you'll overwrite the value you were about to move. Work out which way to walk before you write it. Get it wrong once on purpose so you can see what the output does.
Stuck & Curious  Functions, arrays and strings ▼
warning C4013: 'clamp_health' undefined; assuming extern returning int
You called a function before the compiler had seen it. The compiler reads your file top to bottom, once, and checks every call against what it has already read. Either move the function above main, or put a one-line declaration near the top: int clamp_health(int h); — that's a prototype, a promise that the body exists somewhere further down. Under /WX this warning is a stopped build.
My array prints garbage numbers past the last element
You went off the end. int scores[5] has indexes 0 to 4 — reading scores[5] or higher reads whatever bytes happen to sit after your array, which is usually another variable or leftover junk. C does not check this for you and there's no crash to tell you. Check your loop condition: it should be i < count, not i <= count. That single character is the bug about 90% of the time.
What is '\0' actually — is it the same as the character '0'?
No, and this catches people. '\0' is a byte whose numeric value is zero. '0' is the printable digit, whose value is 48. Try it: printf("%d %d\n", '\0', '0'); prints 0 48. It's the same escape-sequence rule you found in session 1 — the backslash means "the next character is special." You've already used it: char input = '\0'; in your Phase 2 frame loop meant "nothing here yet."
%s printed my name and then a screenful of junk characters
Missing null terminator. %s starts at the address you gave it and prints bytes until it finds a '\0' — no terminator means no stop signal, so it keeps reading memory that isn't yours. Usually you filled the buffer character by character and forgot the last byte, or you used exactly as many boxes as characters with none left for the terminator. char name[3] = "Sam" has nowhere to put it. You need char name[4].
My strcmp check is backwards — it runs when the names DON'T match
The classic. strcmp returns 0 when the strings are equal, negative or positive when they differ — it's answering "how far apart are these," not "are these the same." So if (strcmp(a, b)) runs when they're DIFFERENT, because 0 is false in C and anything non-zero is true. Always write it out in full: if (strcmp(a, b) == 0) for equal, != 0 for different. Never rely on the bare call.
// Curious — the "why" questions
Why do arrays start at 0 and not 1?
Because the index isn't a position, it's a distance. scores[0] means "zero boxes along from the start", scores[3] means "three boxes along". To find any box, the computer takes the address where the array starts and adds index × box size. Starting at 1 would mean subtracting 1 on every single access.
Why can't I copy an array with a = b;?
C simply doesn't allow it — an array name isn't a box you can assign to, and the compiler stops you (C2106). Copy element by element with a loop. Oddly, you can assign a whole struct with =, which you'll meet in Phase 3.5. That inconsistency is pure history from the 1970s.
Why does the compiler need a declaration above main at all?
C was designed to be compiled in one pass, top to bottom, on machines with very little memory. When it reaches a call, it can only check it against what it has already read. A prototype like int clamp_health(int h); is how you tell it in advance. Newer languages read the whole file first, so they don't need this — Godot's GDScript included.

Predict the Output  4 drills — and one you must not run ▼
// Read the fourth one carefully
The first three run and have one right answer each. The fourth deliberately does not, and understanding why is the most useful thing on this page.
1. sizeof versus strlen — they answer different questions
#include <stdio.h>
#include <string.h>

int main(void) {
    char name[32] = "Sam";

    printf("sizeof %d\n", (int)sizeof(name));
    printf("strlen %d\n", (int)strlen(name));
    printf("%d\n", (int)sizeof("Sam"));
    return 0;
}
Write your prediction down, then compile and run it.
Reveal answer 
sizeof 32
strlen 3
4
sizeof is a question about the box, answered by the compiler before the program runs: how many bytes did you reserve. strlen is a question about the contents, answered at runtime by walking forward until it finds a '\0'.

sizeof("Sam") is 4, not 3, because a string literal carries its terminator with it.

One trap for later: sizeof only knows the array size where the array was declared. Pass name to a function and it decays to a pointer — sizeof in there gives you the size of a pointer, not 32. That's why buffer sizes get passed as a separate argument, exactly like fgets(name, NAME_LEN, stdin) does.
2. What strcmp actually promises you
#include <stdio.h>
#include <string.h>

int main(void) {
    int same = strcmp("Sam", "Sam");
    int less = strcmp("Sam", "Sao");
    int more = strcmp("Sao", "Sam");

    printf("%d %d %d\n", same == 0, less < 0, more > 0);
    printf("bare if runs? %d %d\n", same != 0, less != 0);
    return 0;
}
Write your prediction down, then compile and run it.
Reveal answer 
1 1 1
bare if runs? 0 1
Notice this drill prints comparisons, never the raw return values. That's deliberate. The C standard only guarantees the sign: zero for a match, negative if the first string sorts earlier, positive if later. The magnitude is up to the library — MSVC's runtime typically hands back -1, 0 or 1, while other C libraries hand back the difference between the mismatched bytes. if (strcmp(a,b) == -1) is a bug waiting for a different machine.

Line two is the lesson that bites people: if (strcmp(a, b)) runs when the strings are different, because a match returns 0 and 0 is false. Write == 0 or != 0, every time, forever.
3. Moving the stop sign
#include <stdio.h>
#include <string.h>

int main(void) {
    char name[8] = "Samuel";

    printf("[%s] len %d\n", name, (int)strlen(name));
    name[3] = '\0';
    printf("[%s] len %d\n", name, (int)strlen(name));
    printf("%c%c\n", name[4], name[5]);
    return 0;
}
Write your prediction down, then compile and run it.
Reveal answer 
[Samuel] len 6
[Sam] len 3
el
Nothing was deleted. The u, e and l are still sitting in the array exactly where they were — the last printf reads two of them straight out. All you did was move the stop sign, and both %s and strlen honour the first '\0' they meet and never look past it.

This is precisely what name[strcspn(name, "\n")] = '\0'; does to the newline that fgets leaves behind. It doesn't shorten the buffer. It writes a terminator over the '\n'.
4. Do not run this one
int scores[5] = { 40, 95, 12, 78, 63 };
int i;

for (i = 0; i <= 5; i++) {   // <= is the bug
    printf("%d\n", scores[i]);
}
Write your prediction down — then read the answer instead of running it.
Reveal answer
Five real numbers, then a sixth that isn't yours. And there is no correct prediction for the sixth.

scores[5] is off the end of the array. C will happily read the four bytes that happen to sit there: another local variable, leftover stack junk, a zero, anything. The value can change between builds, between debug and release, and between two runs of the same exe. That's undefined behaviour, and its defining feature is that the language makes no promise at all.

Which is why this one isn't a run-it drill. Every other drill in this document has one answer you can check. This one teaches the opposite lesson: a number that comes from off the end of an array means nothing, and a bug that changes every time you run it is far worse than one that fails the same way twice.

MSVC will often flag a constant index like scores[5], and /WX stops the build when it does — but it cannot flag scores[i] when i is a variable it can't predict. The bounds are your job. The loop is i < count. Always.
Quiz Yourself  5 questions — answer out loud before revealing ▼
1. int scores[5]; — what's the index of the last valid element, and what happens if you use scores[5]?
Reveal answer
The last valid index is 4. scores[5] is off the end — and C will do it anyway, reading or writing whatever sits next in memory. No crash, no error, just a corrupted value showing up somewhere unrelated later. That's why every array loop is i < count and never i <= count.
2. char name[32]; — how many characters of actual text can it hold?
Reveal answer
31. The last byte has to hold the '\0' terminator or it isn't a string at all — it's just a pile of chars. This is why fgets(name, 32, stdin) reads at most 31 characters and writes the terminator itself.
3. When does the body of if (strcmp(a, b)) { ... } run?
Reveal answer
When the strings are different — the opposite of what it looks like. strcmp returns 0 for a match, and 0 is false in C. So the bare call is a "not equal" test. Write == 0 or != 0 every single time and this bug can never bite you.
4. You fill a char buffer one character at a time and forget the last step. What does printf("%s", buf) do?
Reveal answer
Prints your characters and then keeps going. %s walks forward from the address it was given until it finds a '\0', and you never wrote one — so it spills out whatever bytes come after the buffer as junk characters, until it happens to hit a zero byte somewhere in memory.
5. Why does printf("Len: %d\n", strlen(name)); break your build under /W4 /WX?
Reveal answer
strlen returns a size_t, not an int, and %d expects an int — so MSVC raises a format mismatch warning and /WX turns it into a stopped build. Same family as the C4244 you hit in session 1: the type and the specifier have to agree. Fix it with an explicit cast, (int)strlen(name), which is you telling the compiler "yes, on purpose."

saving and loading — fopen, fprintf, fscanf, fclose (King ch 22) 
#define _CRT_SECURE_NO_WARNINGS   // first line of the file, before any #include (see below)
#include <stdio.h>

void save_scores(char names[][NAME_LEN], int scores[], int count) {
    FILE* f = fopen("scores.txt", "w");   // "w" = write: creates the file, or wipes it
    int i;
    if (f == NULL) { printf("Couldn't save scores\n"); return; }
    for (i = 0; i < count; i++) {
        fprintf(f, "%s %d\n", names[i], scores[i]);   // printf, but into the file
    }
    fclose(f);   // always close — the last writes may not reach the disk until you do
}

int load_scores(char names[][NAME_LEN], int scores[], int count) {
    FILE* f = fopen("scores.txt", "r");   // "r" = read: NULL if the file isn't there
    int i = 0;
    if (f == NULL) return 0;                     // first run: keep the defaults
    while (i < count && fscanf(f, "%31s %d", names[i], &scores[i]) == 2) {
        i++;                                   // fscanf returns how many values it read
    }
    fclose(f);
    return i;                                   // how many rows actually loaded
}
// Three things that will bite
C4996 — MSVC calls fopen and fscanf "unsafe" and suggests its own fopen_s. Under /WX that's a stopped build. The #define _CRT_SECURE_NO_WARNINGS line switches the warning off. It only works if it comes before the first #include.
%31s — reads one word, at most 31 characters, so it can't overflow char name[32]. One word means a name with a space in it breaks the file. Keep names to one word for now.
scores.txt — is created in whatever folder you ran the program from. If it "doesn't save", check you're running from the same folder each time. Add it to .gitignore: it's data, not code.
Mixed Review  two from Phase 02 ▼
Two questions from earlier phases. Remembering something after a gap is what makes it stay — answer out loud first.
1. [Phase 02] int total = 7, count = 2; then float avg = total / count; — what's in avg, and how do you fix it?
Reveal answer
3.0. Both sides are ints, so the division happens in int and throws away the .5 before the result is stored in the float. Fix it by casting one side first: (float)total / count gives 3.5.
2. [Phase 02] A loop runs for (i = 0; i <= 10; i++). How many passes, and why does that matter more now?
Reveal answer
11 — 0 through 10. With arrays, the condition is the difference between walking every box and reading one box past the end. For an array of 10, the loop is i < 10, which gives exactly 10 passes: 0 through 9.
