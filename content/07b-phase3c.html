Build Spec  Write the requirements before you build ▼
Three requirements per build, written before you open the editor. Each line is something you can test: run the program and answer yes or no. This is the It should: list from the Phase 07 "implement this" prompt, writing it for yourself now is practice for writing it for Claude later. Tick the build when all three pass.

player.h + player.c: it should:

  • keep only the struct and the declarations in player.h, the bodies in player.c, and have main.c include player.h, never player.c
  • never let player_take_damage push health below 0 (and set alive to false at 0), and never let player_heal push it above 100
  • create a Player in main, move it, damage it and heal it, printing after each step, and the printed values change

guess.c split: it should:

  • split Phase 3.5's guess.c into guess.h (the round struct and prototypes, guarded), guess.c (the bodies) and main.c (the game loop), built from one set SOURCES=main.c guess.c line

Starter Code  player.h + player.c ▼
player.h, the declaration (what exists) 
#pragma once
#include <stdbool.h>

// A struct groups related data together
// Think of it as a blueprint for a game object
typedef struct {
    float x;
    float y;
    int   health;
    bool  alive;
} Player;

// Function declarations, the "what" without the "how"
Player player_create(float start_x, float start_y);
void   player_move(Player* p, float dx, float dy);
void   player_take_damage(Player* p, int amount);
void   player_print(const Player* p);
player.c, the definitions (the actual code) 
#include "player.h"
#include <stdio.h>

Player player_create(float start_x, float start_y) {
    Player p;
    p.x      = start_x;
    p.y      = start_y;
    p.health = 100;
    p.alive  = true;
    return p;
}

// Player* means "a pointer to a Player", we pass by pointer
// so the function can MODIFY the original, not a copy
void player_move(Player* p, float dx, float dy) {
    p->x += dx;
    p->y += dy;
}

void player_take_damage(Player* p, int amount) {
    p->health -= amount;
    if (p->health <= 0) {
        p->health = 0;
        p->alive = false;
    }
}

void player_print(const Player* p) {
    printf("Player pos: (%.1f, %.1f) health: %d alive: %s\n",
           p->x, p->y, p->health,
           p->alive ? "yes" : "no");
}

build.bat, multi-file version 
@echo off

set SOURCES=main.c player.c
cl %FLAGS% %SOURCES% /Fe:game.exe
if %ERRORLEVEL% neq 0 (
    echo BUILD FAILED
    exit /b 1
)
echo BUILD OK

Setup  Debugger setup in VS Code ▼
// Four steps, once, forever
1
In VS Code, install the C/C++ extension from Microsoft (ms-vscode.cpptools). That's what provides the cppvsdbg debug type, the one that speaks MSVC and PDB.
2
Open your repo as a folder (File → Open Folder), not as a single file. ${workspaceFolder} only means something if VS Code has a folder open.
3
Create .vscode/launch.json in the repo root and paste the config below. Commit it, your partner gets debugging for free.
4
Run build first, every single time. F5 launches the exe that's on disk. It does not compile for you. This is the number one reason breakpoints "don't work."
.vscode/launch.json, minimal MSVC config 
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Debug game.exe",
      "type": "cppvsdbg",
      "request": "launch",
      "program": "${workspaceFolder}/game.exe",
      "args": [],
      "stopAtEntry": false,
      "cwd": "${workspaceFolder}",
      "environment": [],
      "console": "integratedTerminal"
    }
  ]
}
Practice this  Watch hero change from a function that never names it ▼
// Watch a pointer change, live
The mental models were metaphors. This is the thing itself. Ten minutes, once your main.c (Build Spec) creates hero and damages it with player_take_damage(&hero, ...).
1
Run build. Make sure it succeeded before you touch F5.
2
Open player.c. Put the cursor on the first line inside player_take_damage and press F9.
3
Press F5. The program starts, then freezes on that line with a yellow arrow the first time damage is dealt.
4
Open the Watch panel and add three expressions: p, *p, and p->health.
5
Look at them before you step. p is a 16-digit hex number like 0x000000a3f9d6fba0, that's the address, the piece of paper with the house number on it. *p expands into the whole Player. p->health is one field inside it.
6
Press F10 once. Watch p->health drop. Nothing in this function is named "hero", and hero's health just changed anyway. That is what a pointer does, and you are watching it happen.
7
Now go up to main, add &hero to the Watch panel, and compare it to p. Same number. Same house.
Do the same thing with the photocopy version from Phase 3.5's Break it (The photocopy), player_move(Player p, ...), no asterisk. Watch p.x change inside the function, then step out and watch hero.x sit there untouched. The copy dying at the closing brace, on screen.
Mixed Review  two from Phase 3.5, one from Phase 03 ▼
Three questions from earlier phases. Remembering something after a gap is what makes it stay, answer out loud first.
1. [Phase 3.5] Enemy e = enemies[i]; e.health -= 10; runs, but the enemy in the array keeps its health. Why, and what's the fix?
Reveal answer
e is a copy. Struct assignment copies every field into a new box, so the subtraction lands on the copy, which is thrown away. Take a pointer to the real one instead: Enemy* e = &enemies[i]; e->health -= 10;
2. [Phase 3.5] Inside void show(int scores[]), what does sizeof(scores) give on your x64 build, and why?
Reveal answer
8. An array parameter is really a pointer, so sizeof measures the pointer, not the array. That's why functions that take an array also take its count.
3. [Phase 03] What does static int spawned = 0; inside a function do that int spawned = 0; doesn't?
Reveal answer
It's made once and keeps its value between calls, so it can count every spawn. The plain local is made fresh, set to 0, on every call. This phase adds static's other meaning: on a function or a variable outside every function, it means private to that file.

Claude Code Prompts  Phase 3.75 ▼
// Design the interface first, then ask for the body
When you ask AI for a function, you are choosing its name, what it takes in, what it returns and what it changes. If you don't say, AI invents them, and the invention may not match your game. So write the declaration yourself first, like void player_heal(Player* p, int amount);, and ask AI to fill in only the body. If you can write that line, you understand the function well enough to check what comes back.
// Bad prompt vs good prompt
✗ Bad: you've given up control
"Write a player system for my game"
AI will invent the fields, function names and file structure, and none of it will match what you build later.
✓ Good: you own the architecture
"I have a Player struct with fields: float x, float y, int health, bool alive. Write ONLY the body of player_heal(Player* p, int amount): it should add amount to p->health, cap it at 100, and not change alive. Declaration already exists in player.h."
The struct and the signature are yours. AI wrote the 3 lines inside.
