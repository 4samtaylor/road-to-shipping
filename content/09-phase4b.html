Explain Like I'm New  Why you're building a game with no graphics ▼
// Two hard things, one at a time
Phase 5 was going to teach you two unrelated hard things in the same weekend: how a window works, and how a game is structured. When something breaks — and it will — you'd have no way to tell which of the two you got wrong.

So you build the game structure here, in the terminal, where you can already see everything and every tool you have still works. By the time you open Phase 5, the only new thing in it is the window. Same loop, same states, same collision idea, drawn somewhere else.
What you finish this phase with is a genuine game: it runs on its own, it reacts to keys while it's running, obstacles come at you, you dodge, you score, you die, you restart. It looks like 1978. It is structurally identical to what you'll ship.
// The missing rung — input that doesn't stop the world
Everything you've written so far calls scanf and then stands completely still until you press Enter. A game can't do that. The obstacles have to keep moving whether or not you're touching the keyboard. 
BLOCKING (everything so far)     NON-BLOCKING (a game)
----------------------------     ---------------------
scanf(" %c", &input);            if (_kbhit()) key = _getch();
   ^ the program stops dead          ^ "is a key waiting?" — answers
     until Enter is pressed            instantly either way, then the
                                       loop carries on regardless
_kbhit() from <conio.h> asks one question — is there a keystroke sitting in the buffer? — and returns immediately, non-zero for yes. It never waits.
_getch() takes that keystroke. No Enter needed, and it doesn't echo the character to the screen, which matters when you're drawing the screen yourself.
This is the rung that was missing between scanf and Win32's message queue. Phase 5's PeekMessage is the same idea — "anything for me? no? fine, carry on" — just with a window attached.
// Your session 1 bug is this phase's rendering engine
In session 1 you wrote printf("Lets\r party up!\n") and watched the word "Lets" vanish. That looked like a mistake. It is the technique this whole phase is built on. 
printf("\r%s  score %d", lane, score);

frame 1:  A....#.......#....  score 12
                     ↑ \r sends the cursor back here, column 0,
                       without moving down. No newline, ever.
frame 2:  A...#.......#.....  score 13   ← drawn straight over the top
One line of output, repainted thirty times a second. No scrolling, no flicker, and the terminal never even knows it's being used as a screen.
The obvious alternative, system("cls"), clears the whole console and redraws from nothing — you get a visible flash on every frame, and it launches a separate process each time, which is astonishingly slow. Use \r. You found it first anyway.
Build the entire line in a char array first, then print it in one go. That's a frame buffer — the same thing Phase 5 does with pixels, at a smaller scale.
// Sleep() — why a game has to slow itself down
Left alone, your loop runs millions of times a second. The obstacles would cross the screen before you saw them and your CPU fan would come on. Sleep(33) from <windows.h> hands the processor back to Windows for about 33 milliseconds, which gives you roughly 30 frames a second.

"About" is doing real work in that sentence. Sleep guarantees a minimum, not an exact figure — Windows wakes threads on a scheduler tick that's around 15.6 ms by default, so Sleep(1) is not one millisecond. It's fine for this phase and it's not good enough for a real game, which is exactly why Phase 5 asks you to measure elapsed time instead of assuming it.

Starter Code  ascii_runner.c — the skeleton, six TODOs ▼
ascii_runner.c — add it to build.bat, then run build 
#define WIN32_LEAN_AND_MEAN
#include <windows.h>   // Sleep
#include <conio.h>     // _kbhit, _getch
#include <stdio.h>
#include <string.h>    // memset

#define LANE_LEN   50   // how many characters wide the track is
#define PLAYER_COL 4    // the player never moves sideways. The world moves.
#define MAX_OBS    8    // how many obstacles can exist at once
#define FRAME_MS   33   // ~30 frames a second

// Same enum shape you'll use in Phase 6. Learn it here, reuse it there.
typedef enum {
    STATE_MENU,
    STATE_PLAYING,
    STATE_GAME_OVER
} GameState;

int main(void) {
    char      lane[LANE_LEN + 1];   // +1 for the '\0'. Phase 3.5 rule.
    int       obs[MAX_OBS];         // column of each obstacle, -1 = empty slot
    GameState state   = STATE_MENU;
    int       running = 1;
    int       ducking = 0;
    int       score   = 0;
    int       frame   = 0;
    int       key     = 0;
    int       i;

    for (i = 0; i < MAX_OBS; i++) {
        obs[i] = -1;
    }

    printf("ASCII RUNNER\n");
    printf("D = duck   R = restart   Q = quit\n");
    printf("Press any other key to start.\n\n");

    while (running) {

        /* --- 1. INPUT — never blocks -------------------------------- */
        key = 0;
        while (_kbhit()) {      // drain everything typed since last frame
            key = _getch();     // no Enter needed, no echo to the screen
        }
        if (key == 'q' || key == 'Q') {
            running = 0;
        }

        /* --- 2. UPDATE — one switch, exactly like Phase 6 ------------ */
        switch (state) {
        case STATE_MENU:
            if (key != 0 && running) {
                state = STATE_PLAYING;
                // TODO 1: reset score, frame, ducking and every obs[] slot.
            }
            break;

        case STATE_PLAYING:
            ducking = 0;
            // TODO 2: if key is 'd' or 'D', set ducking = 1 for this frame.

            // TODO 3: move every live obstacle one column toward the player.
            //         An obstacle that goes below 0 has been dodged — set its
            //         slot back to -1 and add 1 to score.

            // TODO 4: every 20 frames, find a free slot (obs[i] == -1) and put
            //         a new obstacle at column LANE_LEN - 1. Tune the 20 later.

            // TODO 5: the hit test. If any obstacle sits exactly on PLAYER_COL
            //         and ducking is 0, state = STATE_GAME_OVER.

            frame++;
            break;

        case STATE_GAME_OVER:
            // TODO 6: on 'r' or 'R', clear the board and go back to
            //         STATE_PLAYING. Same reset as TODO 1 — so write it once,
            //         as a function, and call it from both places.
            break;
        }

        /* --- 3. RENDER — build the whole line, print it ONCE --------- */
        memset(lane, '.', LANE_LEN);
        lane[LANE_LEN] = '\0';

        for (i = 0; i < MAX_OBS; i++) {
            if (obs[i] >= 0 && obs[i] < LANE_LEN) {
                lane[obs[i]] = '#';
            }
        }
        lane[PLAYER_COL] = ducking ? 'c' : 'A';

        // \r sends the cursor back to column 0 without moving down, so the
        // next print lands on top of this one. That is the entire renderer.
        printf("\r%s  score %-4d", lane, score);
        fflush(stdout);   // push it out now — no '\n' means it would sit in the buffer

        /* --- 4. WAIT — give the CPU back ---------------------------- */
        Sleep(FRAME_MS);
    }

    printf("\n\nFinal score: %d\n", score);
    return 0;
}
// It compiles clean and runs before you write a single TODO
That's deliberate. Build it, run it, and you'll see an empty track with a stationary A and a score of 0, repainting quietly forever until you press Q. The engine works. The game isn't written yet. Do the TODOs in order, rebuilding after each one — every single one of them produces something visible on screen, which is the fastest feedback loop you've had so far.

If windows.h itself trips /WX on your SDK version, add /external:anglebrackets /external:W0 to the cl line in build.bat. That tells MSVC to stop applying your warning level to headers you didn't write, which is the right fix rather than turning /WX off.
Stuck?  Real-time terminal problems ▼
The track flickers, or every frame prints on a new line and the screen scrolls
You have a \n somewhere in the frame. One newline anywhere in the render step and the cursor moves down permanently — \r can only get you back to the start of the current line. There must be exactly one printf in the render step, it must start with \r, and it must not contain \n at all. If instead you're getting a visible flash on every frame, you're using system("cls") — delete it. It clears the whole console and spawns a process to do it.
Nothing appears at all until I quit, then everything shows up at once
Output buffering. stdout normally holds characters until it sees a \n or the buffer fills, and your render line deliberately has no newline in it — so it sits there. fflush(stdout) immediately after the printf forces it out. It's already in the skeleton; if you rewrote the render step, you probably dropped it.
Input feels laggy — I press duck and it happens a moment later, or several times
Two separate causes. First, your reaction window is one frame long, so at Sleep(33) a key can wait up to 33 ms before the loop even looks. Lower FRAME_MS to 16 and it halves. Second, holding a key down makes Windows repeat it, which stuffs dozens of characters into the buffer — if you only call _getch() once per frame you're working through a backlog that gets further behind every frame. That's what the while (_kbhit()) loop is for: drain the buffer completely each frame and keep only the last key.
Sleep(16) doesn't give me 60 fps, and Sleep(1) doesn't give me 1000
It never will. Sleep promises "at least this long," and Windows only wakes sleeping threads on a scheduler tick — around 15.6 ms by default. So Sleep(1) typically costs you 1 to 15 ms, and Sleep(16) often lands nearer 31. It's fine for an ASCII game and completely inadequate for a real one. The real fix is not to trust the sleep: measure how long the frame actually took and feed that elapsed time into your movement. That's Phase 5's frame timer task, and in Godot it arrives for free as the delta parameter.

Quiz Yourself  4 questions — answer out loud before revealing ▼
1. Why can't a game use scanf, and what replaces it here?
Reveal answer
scanf blocks — the entire program stops until Enter is pressed, so nothing moves while you're deciding. A game's loop has to keep running whether or not there's input. _kbhit() replaces it by asking "is a key waiting?" and answering instantly either way; _getch() then collects the key without waiting for Enter and without echoing it. Phase 5's PeekMessage is the same trade, with a window attached.
2. Why is the input step a while (_kbhit()) loop rather than a single if?
Reveal answer
Because keystrokes queue up. Hold a key and Windows generates repeats far faster than 30 frames a second, so an if takes one character per frame and falls further and further behind — you'd still be replaying inputs from five seconds ago. The while drains the buffer completely each frame and keeps the most recent key, so the game always reacts to what you're pressing now.
3. Why build the whole track into a char array before printing anything?
Reveal answer
One printf per frame instead of fifty. Printing character by character is slow and you'd watch the line assemble itself, which is exactly what flicker is. Building it in memory first and pushing it out in a single call means the frame appears all at once. That's a frame buffer — the same principle as the back buffer you'll use in Phase 5, and the same reason it exists there.
4. Sleep(16) — do you actually get a 16 ms frame?
Reveal answer
No. Sleep guarantees at least the time you ask for, never exactly it. Windows wakes sleeping threads on a scheduler tick that defaults to about 15.6 ms, so 16 often becomes 31, and Sleep(1) is nothing like a millisecond. It's acceptable here because nothing depends on precision. The real answer is to stop assuming and start measuring elapsed time per frame, then scale movement by it — Phase 5's frame timer, and the delta that Godot hands you automatically in _process.
