Concepts First  Read before writing any code ▼
// What a .c file actually is
A .c file is just a text file. The .c extension tells the compiler "this text is written in the C language." Nothing runs until you compile it. Writing code is writing instructions. Compiling translates those instructions into something the CPU can execute.
// cd vs cl — two completely different things
cd (Change Directory) — navigation. Moves you to a folder in the terminal. Like clicking into a folder in Windows Explorer but with text. You must be in the right folder before compiling.

cl — the actual compiler. Give it a .c filename and it produces a .exe. If your code has errors, it stops and prints which line and why. No .exe is produced until all errors are fixed.

dir — lists files in your current folder. Run this if you're not sure where you are.
// How to think about the compiler
The compiler is a strict editor who speaks machine. You write in human-readable C. The computer speaks only binary. The compiler translates between the two — with zero tolerance for ambiguity. A missing semicolon, a misspelled function, using a variable before declaring it — it stops and refuses to produce anything. This strictness is a feature. It catches mistakes before they become bugs in a running game.

Stuck?  Errors from session 1 + common Phase 1 issues ▼
"'cl' is not recognized as a command"
You're in the wrong terminal. Open a new terminal with Ctrl+` — the VS banner should appear automatically after the settings.json fix. If it doesn't, check that your settings.json was saved correctly and the vcvars32.bat path is correct.
error C2017: unknown escape sequence (the \n error from session 1)
Your \n ended up outside the quotes. It must be INSIDE the string: printf("text\n") not printf("text")\n. \n only means "new line" inside a string. Outside it, the compiler sees a backslash and the letter n — which it doesn't recognise.
I saved but the compiler still uses the old version
Check the tab in VS Code — if there's a dot (●) next to the filename, it's unsaved. Ctrl+S, then compile. The compiler reads from disk. What's on screen doesn't matter until saved.
Program compiles but the window closes immediately
Normal — it runs and exits instantly. Add getchar(); before return 0; to pause. Or run it from the VS Code terminal rather than double-clicking the .exe.
VS Code says "Do you want to install the C/C++ Extension Pack?"
Click Install. Always. This gives you syntax highlighting, error detection, and autocomplete for C. Without it VS Code is just a plain text editor for C files.
Claude Code Prompts  Use these at this phase ▼
// How to think about AI as a coding partner
AI is a fast, tireless implementer — but it has no judgment about your project. It doesn't know your architecture, your conventions, or what you actually need. It will confidently produce code that compiles, runs, and solves the wrong problem.

Your job is to be the architect. AI is the contractor. You design the system, specify the interface, and verify the output. The more precisely you specify, the better the output. Vague prompts produce generic code. Specific prompts produce code that fits.
// Why Phase 1 matters for AI prompting
Right now you understand what printf, return 0, #include, and \n do. That's enough to evaluate AI output at this level.

If you can't read the code, you can't catch when AI makes a mistake. And it will make mistakes — wrong escape sequences, wrong format specifiers, wrong return types. You already know what those look like because you hit them in session 1. Understanding errors makes you immune to confident wrong answers.
// Phase 1 prompts — copy and adapt
When you get a compiler error you don't understand
I'm learning C for the first time. I got this compiler error: [paste full error output here]. Explain what it means in plain language, tell me which line caused it and why, then show me exactly how to fix it.
When you want to understand code line by line
I'm a beginner learning C. Explain this code to me line by line — what each part does, why it's there, and what would break if I removed it: [paste code]
When you want AI to write a printf for you
Write a single printf statement in C that prints: "Player: [name] | Score: [score] | HP: [health]" where name is a string, score is an int, and health is an int. Use the correct format specifiers. Nothing else — just the one line.
// The prompting pattern that works at every phase
Be specific
Name the function, the types, the inputs, the outputs. "make it print stuff" → bad. "write printf that prints an int with %d" → good.
Scope it small
Ask for one thing at a time. AI asked for "a whole game" will make architectural decisions you didn't approve. Ask for one function, one file, one fix.
Read before use
Never paste generated code into your project without reading every line. Understand what it does before it becomes your code.
Push back
If the output is more complex than you need, say so: "simplify this — I don't need [X] yet." AI defaults to thorough. You need minimal and understandable.

build.bat  Stop typing compile commands — automate it ▼
// What a .bat file is and why you want one
A .bat file (batch file) is a plain text file containing a list of terminal commands. When you run it, Windows executes every command inside it in order — exactly as if you had typed them yourself.

Right now your compile command is:
cl hello_world.c That's fine for one file. But as your project grows you'll have multiple .c files, compiler flags, output folders, and linker options. Typing that full command every time is error-prone and slow. A build.bat wraps all of it into one word: build.

Every professional C/C++ project has some form of build automation. This is the simplest version of that concept.
// The analogy
Think of build.bat as a recipe card. Instead of measuring out every ingredient and step every time you cook, you write the recipe once and follow it. Your build.bat is the recipe for turning your source code into a runnable game. One command. Every time. No mistakes.
// Step 1 — Create the file
In VS Code, in your game-dev-exercises folder, create a new file called build.bat. Make sure it's in the same folder as your .c files — not inside a subfolder.
// Step 2 — Start simple: Hello World build
build.bat — Phase 1 version (single file) 
@echo off                        rem  hides the commands from printing to terminal

rem ── Compile ──────────────────────────────────────────
cl hello_world.c /Fe:hello_world.exe   rem  /Fe: sets the output .exe name

rem  Check if compile succeeded — %ERRORLEVEL% is 0 on success
if %ERRORLEVEL% neq 0 (
    echo.
    echo  BUILD FAILED.
    exit /b 1
)

echo.
echo  BUILD OK — hello_world.exe
// Step 3 — Run it
In your terminal, just type: build That's it. Windows finds build.bat, runs every line inside it, and either reports BUILD OK or BUILD FAILED with the compiler error. Then run your .exe as normal.
// Step 4 — Grow it as your project grows
build.bat — Phase 3+ version (multiple files) 
@echo off

rem ── Compiler flags ────────────────────────────────────
rem  /W4      = turn on most warnings (your compiler catching mistakes)
rem  /WX      = treat warnings as errors (no silent problems)
rem  /Zi      = include debug info (lets you use the debugger)
rem  /Od      = disable optimisation (faster compile during dev)
rem  /Fe:     = name the output .exe
set FLAGS=/W4 /WX /Zi /Od

rem ── Source files — add new .c files here as you create them ──
set SOURCES=main.c player.c

rem ── Compile ───────────────────────────────────────────
cl %FLAGS% %SOURCES% /Fe:game.exe

if %ERRORLEVEL% neq 0 (
    echo.
    echo  BUILD FAILED.
    exit /b 1
)

echo.
echo  BUILD OK — game.exe
// What the flags actually do — read this
/W4 — turns on most compiler warnings. The compiler will flag things that look suspicious even if they technically compile. These warnings are almost always real problems.
/WX — treats warnings as errors. Your build fails if there are any warnings. This forces you to write clean code. Standard in professional game studios.
/Zi — includes debug information in the .exe. Required if you want to use a debugger to step through code line by line and inspect variable values — which you will need.
/Od — disables compiler optimisations. Faster compile time during development. When you ship, swap to /O2 for a faster executable.
set SOURCES= — this is where you list every .c file in your project. Adding a new source file = add it here. One place, always correct.

Predict the Output  4 drills — guess first, then run it ▼
// How these work
Read the code. Write your prediction down on paper — not in your head, on paper, because your head will quietly agree with whatever comes out. Then compile it and compare. The ones you get wrong are the only ones that teach you anything. Session 1 was accidentally this exercise; this is the deliberate version.
1. The \r you found by accident in session 1
#include <stdio.h>

int main(void) {
    printf("Lets\r party up!\n");
    return 0;
}
Write your prediction down, then compile and run it.
Reveal answer
It prints party up! — with a leading space, and no sign of "Lets" at all.

\r is carriage return: send the cursor back to column 0 of the same line without moving down. \n is the one that moves down. So "Lets" gets printed, the cursor jumps back to the start, and " party up!" is painted straight over the top of it. Ten characters covering four — nothing survives.

You didn't break anything in session 1. You found the oldest trick in terminal rendering, and in Phase 4.5 you'll use it deliberately to redraw a whole game every frame.
2. Two backslashes and two percent signs
#include <stdio.h>

int main(void) {
    printf("C:\\Users\\4samt\\new%%directory\n");
    printf("backslash: \\ percent: %%\n");
    return 0;
}
Write your prediction down, then compile and run it.
Reveal answer 
C:\Users\4samt\new%directory
backslash: \ percent: %
Two doubled characters, two completely different reasons. \\ is the compiler's rule — inside a string literal a backslash starts an escape sequence, so one backslash needs two. That's resolved before your program ever runs.

%% is printf's rule — a percent sign starts a format specifier, so printf needs two to print one. That happens at runtime, inside printf. If you ever print a string that came from somewhere else with printf(text), a stray % in it will make printf go looking for an argument you never passed. Use printf("%s", text).
3. Truncation — the C4244 from session 1, on purpose this time
#include <stdio.h>

int main(void) {
    float x = 1.8f;
    int   n = (int)x;

    printf("%d\n", n);
    printf("%.1f\n", x);
    printf("%d\n", (int)9.99f);
    return 0;
}
Write your prediction down, then compile and run it.
Reveal answer 
1
1.8
9
float to int truncates toward zero. It does not round. 1.8 becomes 1 and 9.99 becomes 9 — the fraction is thrown in the bin, not weighed up.

This is exactly what int var(float x) { return x; } was doing silently in session 1, and why the compiler raised C4244. Note that x itself is untouched — it still prints 1.8. The (int) cast doesn't change the behaviour one bit; it changes the conversation with the compiler from "you might not have meant this" to "I meant it."
4. Four printfs, how many lines?
#include <stdio.h>

int main(void) {
    printf("A");
    printf("B\n");
    printf("C\nD");
    printf("E\n");
    return 0;
}
Write your prediction down, then compile and run it.
Reveal answer
Three lines from four calls:
AB
C
DE
printf never adds a newline for you. The breaks land exactly where you put \n and nowhere else — which means one printf can produce two lines, and two printfs can produce one.

This is why the command prompt sometimes reappears glued to the end of your last word: you forgot the \n on the final line.
Quiz Yourself  5 questions — answer out loud before revealing ▼
1. What does \r do, and why did "Lets" disappear from your output?
Reveal answer
\r is carriage return. It snaps the cursor back to the start of the current line without moving down a line. You printed "Lets\r party up!\n" — so "Lets" was printed, the cursor jumped back to column 0, and " party up!" was typed straight over the top of it. Nothing was deleted. It was overwritten.
2. 1.8f goes into a function that returns int. What comes out, and why?
Reveal answer
1. Not 2. Float to int truncates — the decimal part is chopped off, not rounded. That's what warning C4244: possible loss of data was telling you. 7.9f would give 7, and -1.8f would give -1 (toward zero).
3. Why do you have to write \\ to print one backslash, and %% to print one percent sign?
Reveal answer
Inside a printf string, both characters are already doing a job. A backslash starts an escape sequence (\n, \t) and a percent starts a format specifier (%d, %f). Doubling them says "I mean the symbol itself, not the instruction." That's why your path printed as C:\User\4samt\new%directory.
4. You changed the code, hit build, and the output is identical. First thing to check?
Reveal answer
Whether you saved. Look for the dot (●) on the VS Code tab. The compiler reads the file from disk — it has no idea what's on your screen. Ctrl+S, then build. Second thing to check: did the build actually succeed, or did you get BUILD FAILED and then run a stale .exe from the last good compile?
5. What does return 0; at the bottom of main actually tell anyone?
Reveal answer
It tells the operating system the program finished cleanly. 0 means success, anything else means failure. That's the exact same value your build.bat reads as %ERRORLEVEL% — which is how the if %ERRORLEVEL% neq 0 line knows to print BUILD FAILED.
