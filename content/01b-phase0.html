Start here  Why this phase comes before any code ▼
C is a thin layer over the machine. Most of what makes it confusing at first (why an int has a limit, what an address is, why a local variable vanishes, why a key press waits for Enter) is really about the computer underneath. This phase shows you that computer first, in nine short pages, so the C in Phase 01 has something to hang on.
You won't type any code here. Each concept has a tiny program or a diagram to read, a check to answer, and a pen-and-paper task. The programs all build with your setup, so come back and run them once Phase 01 has shown you how.

Predict the Output  2 drills, guess first, then check ▼
// Read, don't run (yet)
Both programs build cleanly with your setup. Predict on paper now; after Phase 01, compile and run them to check yourself.
1. One number, two spellings
#include <stdio.h>

int main(void) {
    unsigned int health = 0x64;
    unsigned int max = 255;

    printf("health %u = %x\n", health, health);
    printf("max %u = %x\n", max, max);
    return 0;
}
Write your prediction down, then reveal.
Reveal answer 
health 100 = 64
max 255 = ff
0x64 is 6 sixteens and 4 ones: 96 + 4 = 100. %u spells it in decimal, %x in hex with no 0x and lowercase letters. 255 is the biggest byte, all eight bits on, which is ff.
2. Which frames are alive?
#include <stdio.h>

int heal(int hp) {
    int potion = 25;
    return hp + potion;
}

int main(void) {
    int health = 60;
    health = heal(health);
    health = heal(health);
    printf("health %d\n", health);
    return 0;
}
Predict the output, and how many frames are on the stack at most.
Reveal answer 
health 110
60 + 25 is 85, then 85 + 25 is 110. At most two frames are live: main and one heal. The first heal's frame is popped before the second call starts, so the second potion is a fresh variable in a fresh frame, not the old one.
Quiz Yourself  3 questions, answer out loud before revealing ▼
1. A colour is stored as 0x3366FF. How many bytes is that, and what is the green byte in decimal?
Reveal answer
Three bytes: two hex digits each. Green is the middle pair, 0x66: 6 sixteens and 6 ones, 96 + 6 = 102.
2. A function makes a local variable, returns, and is called again. Is the old value still there?
Reveal answer
No. The local lived in the function's stack frame, and that frame was popped at return. The next call gets a new frame, and its variable starts fresh (or holds leftover junk, if you didn't give it a value). Phase 03 shows the one exception, static.
3. cl prints an error starting with LNK. Which step failed, and what was it looking for?
Reveal answer
The link step (link.exe). Every file compiled, but some name used in one .obj, a function usually, wasn't defined in any .obj or library in the build. Often a .c file was left off the command.

Stuck & Curious  Common questions at this stage ▼
Binary conversions keep coming out wrong
Write the place values above the digits every time (128 64 32 16 8 4 2 1 for a byte) and add only the ones under a 1. For hex, split the bits into groups of four from the right. Check in Calculator's Programmer mode until it's automatic.
I can't read the C in these programs yet
That's expected. Read the walkthrough notes instead of the code, and focus on the idea each program shows. Phase 01 starts the C from zero; come back here afterwards and the programs will read easily.
Do I need to memorise the register names?
No. Remember three: RIP (where the CPU is in the code), RSP (the top of the stack) and RAX (where a function's answer comes back). You'll only meet the others in the debugger's Registers window, if at all.
