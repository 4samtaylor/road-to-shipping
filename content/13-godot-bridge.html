Read This First  You are not going to write your game in C ▼
// The thing this document never said out loud
The games get built in Godot 4, in GDScript. That's settled — it's why GameMaker was ruled out (both games have to share one engine) and why Unity was ruled out (MIT licence, no runtime-fee surprises, and Godot's scene instancing already thinks the way the ARPG needs to). Not a line of C ships in either game.

So the honest question is why seven phases of C, and the honest answer is that C is the only language that refuses to hide anything from you.
// Where this curriculum came from
The shape of this roadmap isn't Claude's idea. It came from an industry programmer's advice — learn low-level C, learn what a window and a message loop actually are, don't start inside an engine that does the thinking for you. That advice got combined with a structured phase plan, and the result is the seven phases you've been working through.

It's advice worth taking for one specific reason: the alternative is a person who can make things happen in an engine but has no idea what the engine is doing, and the moment something breaks below the surface, they're stuck waiting for someone else.
// What the C actually buys you in GDScript
You'll debug better. GDScript hides types, memory and references — until a bug drags them back into view. "Why did changing this enemy change all of them?" is a five-minute problem if you know what a reference is and a lost afternoon if you don't. You'll have watched p->health mutate through a pointer in the debugger. That's the whole answer.
You'll read engine docs and engine source. Godot itself is written in C++. When the documentation says a Resource is reference-counted, or that PackedByteArray is contiguous, those sentences mean something concrete to you now. Most people using the engine skim past them.
You'll be able to work with Person A. They take the complex systems; your job is to contribute real code and review theirs honestly. That requires knowing what the code does, not just that it runs — and the fastest way to learn that is a language that makes you say it explicitly.
You'll write better prompts. Phase 7's whole premise. You cannot verify code you don't understand, and AI writes plausible, confident, subtly wrong GDScript exactly as readily as it writes C.
// The one-sentence version
GDScript lets you skip learning what the machine does. C makes you learn it once, and then GDScript is just a faster way to say things you already understand.
The Transfer Table  Every C concept, and what it becomes in Godot 4 ▼
What you learned in C
What you'll write in Godot 4
typedef struct { ... } Player;
A script is a class. class_name Player extends Node2D, fields become var. Pure data with no behaviour becomes a Resource — that's how item definitions and card data will be stored.
while (running) { ... }
You don't write the loop. Godot owns it and calls _process(delta) every frame, _physics_process(delta) at a fixed rate for movement and collision.
Measuring frame time yourself
The delta parameter. Already measured, handed to you, in seconds. Every Phase 5 frame-timer headache, gone.
enum + switch + break
enum + match. Same idea, no break — match never falls through, so the bug where you forget one can't happen.
Player* p, &hero, *p, p->health
Everything is already a reference. There is no & and no * in GDScript. You pass the object, the function changes the real thing, always. Always ., never ->.
b = a; copies the whole struct
var b = a gives you a second name for the same object. This is the reversal that catches C people. Want a copy? Ask for one: a.duplicate().
aabb_overlap(...) written by hand
Area2D and CharacterBody2D — the physics engine does it and emits body_entered. You still know exactly what it's doing, which is why you'll trust it and know when it's lying.
Enemy enemies[10]; fixed size
var enemies: Array[Enemy] = [] — grows on its own, append() and erase(). No sentinel slots, no shifting by hand. But you'll know why it costs something.
char name[32], '\0', strlen
String is a real type. name.length(), == compares contents. No terminator, no buffer size, no strcmp return-value trap.
int vs float, casts, truncation
Still real, still matters. Typing is optional in GDScript — use it anyway. var health: int = 100 catches the same class of bug your /W4 /WX flags catch.
#include "player.h", .h/.c split
No headers at all. preload("res://player.gd"), or give the script a class_name and it's visible everywhere.
build.bat, cl /W4 /WX /Zi
No compile step. Scenes (.tscn) and export presets replace the build. Press F5 in the editor and it runs.
printf debugging, the VS Code debugger
print() and Godot's own debugger — breakpoints, step, a live variable panel, and a remote scene tree that shows you every node while the game is running.
Same Logic, Two Languages  Three side-by-side comparisons ▼
// 1. The Player — struct and functions become a class
player.h + player.c — C
typedef struct {
    float x;
    float y;
    int   health;
    bool  alive;
} Player;

void player_move(Player* p,
                 float dx, float dy) {
    p->x += dx;
    p->y += dy;
}

void player_take_damage(Player* p,
                        int amount) {
    p->health -= amount;
    if (p->health <= 0) {
        p->health = 0;
        p->alive = false;
    }
}

// caller has to hand over the address
player_take_damage(&hero, 10);
player.gd — GDScript (Godot 4)
class_name Player
extends CharacterBody2D

# x and y already exist as .position
var health: int = 100
var alive: bool = true

func move(dx: float, dy: float) -> void:
    position.x += dx
    position.y += dy

func take_damage(amount: int) -> void:
    health -= amount
    if health <= 0:
        health = 0
        alive = false

# no address, no pointer, no &
# hero IS a reference already
hero.take_damage(10)
Notice what vanished: the Player* parameter, the & at the call site, and every ->. The function no longer needs to be told which player — it is the player. And it still mutates the real object, for exactly the reason Player* did in C. Same mechanism, no syntax for it.
// 2. The state machine — switch becomes match
game.c — C
typedef enum {
    STATE_MENU,
    STATE_PLAYING,
    STATE_GAME_OVER
} GameState;

switch (g->state) {
case STATE_MENU:
    if (key != 0) {
        g->state = STATE_PLAYING;
    }
    break;

case STATE_PLAYING:
    update_player(g);
    if (g->player.health <= 0) {
        g->state = STATE_GAME_OVER;
    }
    break;

case STATE_GAME_OVER:
    if (key == 'r') {
        game_reset(g);
    }
    break;
}
game.gd — GDScript (Godot 4)
enum State { MENU, PLAYING, GAME_OVER }

var state: State = State.MENU

func _process(delta: float) -> void:
    match state:
        State.MENU:
            if Input.is_action_just_pressed("start"):
                state = State.PLAYING

        State.PLAYING:
            update_player(delta)
            if player.health <= 0:
                state = State.GAME_OVER

        State.GAME_OVER:
            if Input.is_action_just_pressed("restart"):
                reset()

# no break — match never falls through
# indentation is the block, not braces
This is the closest translation in the whole table. The enum is the same idea, the branches are the same branches — you've just stopped writing break, because match can't fall through into the next case. One entire category of bug deleted by the language.
// 3. The game loop — you stop writing it
main.c — C
float speed = 200.0f;   // pixels/sec

while (running) {
    handle_input(&game);

    // you measured dt yourself
    if (right_held) {
        game.player.x += speed * dt;
    }

    render(&game);
    Sleep(16);   // and hoped
}
player.gd — GDScript (Godot 4)
const SPEED := 200.0   # pixels/sec

# Godot owns the loop and calls this
# every frame. delta is your dt,
# already measured, in seconds.
func _physics_process(delta: float) -> void:
    var dir := Input.get_axis("move_left", "move_right")
    velocity.x = dir * SPEED
    move_and_slide()

# no while, no Sleep, no render call.
# The scene tree draws itself.
The loop didn't disappear — Godot is running it and calling you, which is precisely the inversion Phase 5 taught you with Win32's message loop. You already know what delta is for, why speed * delta and not speed, and why _physics_process is the one to use for movement. Most people learn all three the hard way, from a bug.
Don't Over-Invest  What does NOT transfer, and how much to care ▼
// Learn the shape, skip the trivia
Some of what's in this roadmap is a concept you'll use forever. Some of it is Windows-specific plumbing you will genuinely never type again. It's worth knowing which is which before you spend a weekend memorising the wrong one.
Win32 API specifics — WndProc, WM_PAINT, HWND, WPARAM, the message queue
Understand the inversion — that the system calls you rather than the other way round — because that's exactly how _process and signals work in Godot. Then let the rest go. LRESULT, WNDCLASS and the registration boilerplate are 1993 trivia; even Win32 programmers copy that block rather than remember it. Phase 5 says 20% comprehension on a first read is the right outcome, and it means it.
Manual memory — malloc, free, ownership, leaks, allocators
Know what a heap allocation is and what a dangling pointer is, at concept level, because that vocabulary explains half of Godot's behaviour (queue_free(), reference counting, why a freed node's reference goes invalid). Do not go further. GDScript reference-counts and frees for you, and weeks spent on custom allocators are weeks not spent on your game. If either project ever needs that level of control, it's Person A's problem and it'll be in C++.
MSVC flags and build tooling — /W4, /WX, /Zi, /Fe:, vcvars32.bat, build.bat
Pure MSVC trivia and worth exactly what it cost you. The habit transfers and matters enormously: warnings on, warnings as errors, fix them at the source. In GDScript that habit becomes typing your variables and keeping the editor's warning panel empty. The flags themselves you'll forget within a month of moving over, and that's fine.
Header files, declaration vs definition, #pragma once
Gone entirely. GDScript has no headers, no forward declarations and no include order. What survives is the instinct behind them — design the interface before the implementation, which is Phase 3's actual lesson and Phase 7's whole method. Writing func take_damage(amount: int) -> void: before you write the body is the same discipline in a different language.
C string handling — char arrays, '\0', strlen, strcmp, buffer sizes
Godot's String makes all of it unnecessary, and == compares contents the way you always wanted it to. Keep one thing: the awareness that text is bytes in memory somewhere, which is why PackedByteArray, encoding and save-file corruption make sense to you when they come up. Don't drill string.h any further than Phase 3.5 goes.
The Trigger Point  When to stop learning C and open Godot ▼
// The condition, stated exactly
When Phase 6's checkpoint is fully ticked, you're done with C. Not Phase 7 — that one is ongoing and always will be. Phase 6.

Three states transitioning correctly, a player moving on screen with collision detected, and a partner who can clone the repo and run it without asking you anything. That's the bar. The moment it's met, open Godot and don't look for one more C thing to learn first.
There is a real failure mode here and it has a name: staying in the comfortable part. C will always have another concept in it. The point was never to finish C — it was to stop being someone who can only use tools they don't understand, and Phase 6 is where that's achieved.
// The first weekend in Godot — the calibration exercise
Don't start the real game. Rebuild the Phase 4.5 ASCII runner as a Godot scene instead: a sprite, obstacles scrolling toward it, jump and duck, score, game over, restart. You already know exactly what it should do, so every minute goes into learning the engine rather than deciding the design.

It'll take a fraction of the time it took in C, and that gap is the lesson — you'll feel precisely how much the engine is doing for you, and you'll know what each of those things actually is.
// Then: the runner, then the ARPG. And why that order.
Game 1 is a 2D infinite runner shooter with ARPG-style loot. Game 2 is the real target — a deck-building dungeon crawler with ARPG progression, somewhere between Slay the Spire, Isaac and Path of Exile.

Game 1 is not a warm-up you throw away. Both games live in the same engine on purpose, and six systems were mapped to carry straight across:
Built for the runner
Becomes, in the ARPG
Directional input handler abstraction
2D sidescroll → top-down 8-directional
Loot tables with prefix/suffix affixes
Full ARPG item generation
Stat modifier stack (flat, percent, additive)
Character sheet and skill scaling
ECS-based enemy AI
Dungeon monsters and bosses
Damage type flags (physical, fire, lightning)
Elemental resistance system
Procedural chunk spawning
Dungeon room generation
Read that table with what you now know. A stat modifier stack is a struct with an array of modifiers and a function that folds them. Damage type flags are bit flags. Procedural chunk spawning is an array of objects being recycled — which is the sentinel-slot pattern from the ASCII runner, at scale. None of this is unfamiliar any more.
// What your job actually is once you're in the engine
Person A takes the complex systems. That was always the arrangement and it's the right one — they're a professional and the timeline is tight enough as it is. Your job is to take real, appropriately scoped work and to be able to read and question everything else.

That's why the C mattered, and it's the only measure of whether this roadmap worked: not whether you can write a linked list, but whether you can look at Person A's item-generation code, follow it, and ask a question that turns out to be worth asking.
