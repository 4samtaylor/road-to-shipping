Explain Like I'm New  From console to window — what actually changes ▼
// Read this before you look at the code below
This is the steepest step in the whole roadmap, and it's not because the code is harder. Everything you've written so far has been in charge of itself. From here, it isn't. That single change is what makes Win32 feel alien, and it's worth understanding before you read a line of it.
// Your program stops being in charge
A console program runs top to bottom. It decides when to print. When it wants input it calls scanf and everything stops dead until the user hits Enter. You call the system.

A windowed program is the other way round. Your window is one of fifty things on the desktop, and Windows owns the mouse, the keyboard and the screen. It decides when your window needs redrawing, when a key was pressed, when the user clicked the X. The system calls you. 
CONSOLE                          WINDOWED
-------                          --------
you print                        you ask Windows "anything for me?"
you call scanf and wait          Windows hands you a message
nothing happens without you      Windows calls WndProc, you react
program ends when main ends      program ends when Windows says so
That inversion has a name — event-driven. It's why there's a function in the starter code you never call yourself. WndProc is your phone number: you hand it to Windows once, and Windows rings it whenever something happens.

// About the wall of types you're about to hit
LRESULT, HWND, WPARAM, LPSTR, HINSTANCE, WNDCLASS. It looks like a different language. It isn't — they're renamed versions of types you already know. HWND is a pointer with a fancy name. WPARAM is a number. Win32 is from 1993 and it named everything twice.

Understanding about 20% of this file on the first read is the correct outcome. Nobody memorises the boilerplate. Real Win32 programmers copy the same window setup they've copied for years and spend their attention on the two places that matter: the switch inside WndProc, and the while loop in WinMain. Those two you should genuinely understand.

Everything else is a form you fill in once. You already have the mental model that matters — you built the loop in Phase 2, the array in Phase 3, and the struct in Phase 3.5. This phase just wires them to a screen.

Starter Code  win32_window.c ▼
win32_window.c — compile: cl win32_window.c user32.lib gdi32.lib 
#include <windows.h>

// Global state — keeps track of our rect position
static int g_rect_x = 100;
static int g_rect_y = 100;
static HWND g_hwnd = NULL;

// Windows calls this function for every event (key press, mouse move, close, etc.)
LRESULT CALLBACK WindowProc(HWND hwnd, UINT msg, WPARAM wp, LPARAM lp) {
    switch (msg) {
        case WM_KEYDOWN:
            if (wp == VK_LEFT)  g_rect_x -= 5;
            if (wp == VK_RIGHT) g_rect_x += 5;
            if (wp == VK_UP)    g_rect_y -= 5;
            if (wp == VK_DOWN)  g_rect_y += 5;
            InvalidateRect(hwnd, NULL, TRUE); // Tell Windows to redraw
            break;
        case WM_PAINT: {
            PAINTSTRUCT ps;
            HDC hdc = BeginPaint(hwnd, &ps);
            FillRect(hdc, &ps.rcPaint, (HBRUSH)(COLOR_WINDOW+1)); // Clear
            RECT r = { g_rect_x, g_rect_y, g_rect_x+50, g_rect_y+50 };
            FillRect(hdc, &r, CreateSolidBrush(RGB(0,200,100)));
            EndPaint(hwnd, &ps);
        } break;
        case WM_DESTROY:
            PostQuitMessage(0);
            break;
        default:
            return DefWindowProc(hwnd, msg, wp, lp);
    }
    return 0;
}

int WINAPI WinMain(HINSTANCE hInst, HINSTANCE hPrev, LPSTR lpCmd, int nShow) {
    // Register the window class
    WNDCLASS wc = {0};
    wc.lpfnWndProc   = WindowProc;
    wc.hInstance     = hInst;
    wc.lpszClassName = "GameWindow";
    wc.hCursor       = LoadCursor(NULL, IDC_ARROW);
    RegisterClass(&wc);

    // Create the window
    g_hwnd = CreateWindowEx(0, "GameWindow", "My First Window",
                   WS_OVERLAPPEDWINDOW, CW_USEDEFAULT, CW_USEDEFAULT,
                   800, 600, NULL, NULL, hInst, NULL);
    ShowWindow(g_hwnd, nShow);

    // The message loop — this IS the game loop at the OS level
    MSG msg;
    while (GetMessage(&msg, NULL, 0, 0)) {
        TranslateMessage(&msg);
        DispatchMessage(&msg);
    }
    return (int)msg.wParam;
}

Stuck?  Win32 specifics ▼
Linker errors about unresolved user32 or gdi32 symbols
You need to link the Windows libraries. Compile with: cl win32_window.c user32.lib gdi32.lib. These libraries contain the actual implementations of CreateWindow, GetMessage, etc.
The rectangle doesn't move smoothly — it flickers
That's GDI — it's not designed for smooth animation. It's expected here. The lesson is: understand what Win32 gives you and why game engines replace it with GPU-based rendering. When you move to SDL2 or OpenGL, this goes away.
I don't understand what LRESULT, HWND, WPARAM etc. mean
These are Windows type aliases — HWND is a "handle to a window" (essentially a pointer), LRESULT is a long integer result, WPARAM/LPARAM are message parameters. You don't need to memorize them — just know they're Windows-specific names for ordinary types. The concepts (callback functions, event loops) are universal.
Claude Code Prompts  Phase 5 ▼
// Win32 is where AI is most dangerous to blindly trust
Win32 has decades of boilerplate, deprecated functions, and platform-specific quirks. AI knows all of them — which means it can write code that compiles, runs, and is completely wrong for what you need. It might use an old API, add features you didn't ask for, or structure the message loop in a way that will fight with your game loop later.

The rule for this phase: use AI to understand, not to generate. Read the starter code until you understand every line. Ask AI to explain, not to write. When you do ask it to write, describe exactly which function to touch and what not to change.
// The "don't rewrite my file" instruction — use it every time
When you have working code and want to add one thing, AI's default is to rewrite the whole file "to be cleaner." This replaces code you understand with code you don't — and often breaks the structure you built deliberately.

Always include: "Don't rewrite my whole file. Show me only the code to add and where to put it."
Understand each Win32 function before using it
I'm learning Win32 in C. Don't write any code. Explain what each of these does in plain English and why it must be called in this order: RegisterClass, CreateWindowEx, ShowWindow, GetMessage, TranslateMessage, DispatchMessage. Then explain what would happen if I removed TranslateMessage.
Add one specific thing without touching the rest
I have a working Win32 window in C with a message loop. I want to add WASD movement alongside the existing arrow key controls. Show me ONLY the 4 lines to add inside the WM_KEYDOWN case — don't rewrite my whole file, don't add new functions, don't change the structure.
Add a frame timer — surgical insertion
I have a Win32 message loop in C. I want to cap it at 60fps using QueryPerformanceCounter and print the frame time in milliseconds. Show me: (1) where to declare the timer variables, (2) the exact code to add inside the loop. Don't touch anything else in my file. Here's my current loop: [paste loop]
Connect your Player struct to the window
I have a Player struct in C (float x, float y, int health, bool alive) and a Win32 window that draws a green rectangle at g_x, g_y. I want to replace the global g_x/g_y with a Player instance and call player_move() on key input. Tell me exactly what to change — don't rewrite the whole file, just the 3-4 spots that need updating.
// The "surgical edit" mindset
As systems get more complex, the most valuable thing you can do with AI is describe the minimum change needed, not the desired end state. "Make my game have WASD movement" gives AI permission to restructure everything. "Add 4 lines inside WM_KEYDOWN for WASD" gives it a precise, verifiable scope.

Surgical prompts → small diffs → easy to read → easy to understand → easy to commit with confidence.
